## 问题与证据

P4-01..P4-04 已产出 PresenceDirectory port（InMemory/Redis 双 adapter）、OutboxPublisher port（KafkaPublisher）、幂等 Delivery consumer（OutboxEventConsumer/KafkaEventConsumer/WakeupProgressHandler）。本卡把它们接成 **P4 生产投递闭环**（计划 §8 P4-05）：Delivery 只发到 Presence 指向的 GatewayId+SessionEpoch；旧 epoch 收包丢弃并触发重路由；本地/跨节点共用同一 ACK 与 MessageId 语义。现状证据（当前 checkout `main @ ec0c85c`）：

- **PresenceDirectory 只有契约测试，生产未接线**：`ProtocolCodec.cpp` 的 `MessagingWiring`（:60-87）无任何 presence 成员——wiring 只有 store/messaging/sink/wakeup/relay；`RedisPresenceDirectory`（RedisPresenceDirectory.hpp/.cpp）与 `InMemoryPresenceDirectory` 的消费方只有 `tests/unit/PresenceContractTest.cpp`、`RedisPresenceContractTest.cpp`。登录（ChatService.cpp:213-331）、登出（:391-446）、断开（:658-703）路径没有 claim/release/renew 调用。
- **投递不经 Gateway/epoch 校验**：`SessionDeliverySink::deliver`（SessionDeliverySink.cpp:129-173）直接 `registry_->lookupByUser(attempt.recipient)` → `conn->send`，无 GatewayId/ConnectionId/SessionEpoch 概念，也无 deliver 前 locate。cluster-context-map §3"跨节点投递永远校验目标 GatewayId+SessionEpoch"无代码落点。
- **单进程内没有 Gateway 概念**：`main.cpp`（:95-230）启动两个 ChatServer 监听实例，无 GatewayId 注入；`GatewayId/ConnectionId/SessionEpoch/DeliveryRoute` 值类型只在 `PresenceDirectory.hpp`（:32-96）定义，无生产接线。ConnectionId 与 ChatService.cpp:19-22 `connectionKey`（连接对象地址低 32 位）无关联。
- **P4-03 CF-1 债务**：`LocalOutboxRelay.cpp` 的 `publisher_.publish` 在 relay `mutex_` 内执行（`scanLocked`/`workerLoop` 持锁调用，P4-03 卡 §Port 替换设计决定登记）——生产 relay 出口当前是 `LocalWakeupPublisher`（ProtocolCodec.cpp:79，无 broker I/O、延迟近零）；P4-05 接 `KafkaPublisher` 时须将 publish 移出锁或接受该延迟为既定代价。
- **P4-02 债务（L-7/L-9）**：内置最小 RESP 客户端 `RedisConn` 无命令/回复的长度与嵌套深度上限（恶意/异常大数组与深嵌套回复未设界），且无 AUTH 密码认证、无 TLS（明文直连，P4-02 卡登记"P4-05 接生产 wiring 前必须补齐（长度/深度有界化 + AUTH/TLS）"）。本卡生产接线用 Redis → **RESP 有界必须补齐**；AUTH/TLS 可因测试实例无密码登记延后。
- **P4-04 consumer 生产 poll 留白**：P4-04 卡 D1"生产接线由 P4-05 决定"——`OutboxEventConsumer` 无内部后台线程，poll 驱动由测试/后续 wiring 调用。

## 设计决定（开卡定案）

- **D1 生产投递闭环 = relay→KafkaPublisher + 生产 consumer poll**（ADR-0002"broker 是跨 Gateway 事件总线"落地）：生产 relay 出口从 `LocalWakeupPublisher` 换为 `KafkaPublisher`（触发 CF-1）；同时把 P4-04 的 `KafkaEventConsumer`（topic `muduo-outbox`、group `muduo-outbox-consumer`）+ `WakeupProgressHandler` 以生产 poll loop 接进 wiring——本地/跨节点全部投递经同一 durable 路径，ACK 与 MessageId 语义与单机完全一致。替代方案（生产保留 LocalWakeupPublisher 双出口）否决：制造第二 wakeup 触发面，违背 P4-05"不出现第二套消息状态机"；LocalWakeupPublisher 保留为测试/回退 adapter。
- **D2 GatewayTransport port + in-process/recording 双 adapter**（计划 §8 P4-05"先 in-process GatewayTransport/recording adapter"）：单 Gateway 生产拓扑下本地投递仍走 sink 直投，跨 Gateway 投递（测试以两个 in-process 实例模拟）经 transport 按 DeliveryRoute 路由。**不拆真实多进程 Gateway、不做 v2 TCP RPC adapter**——in-process 已足以证明 epoch/routing 契约（GREEN 记录理由，登记为本卡不拆的决策证据；真实拆进程属 P4-06 三节点拓扑）。
- **D3 投递路径接线 seam = Gateway 感知的 sink wrapper**：在 `DelegatingDeliverySink` 与 `SessionDeliverySink` 之间插入 deliver 前 locate 校验（无条目=离线、本地匹配=直投、跨节点=transport、epoch 不匹配=丢弃+重路由）。不动 DeliveryCoordinator/ReliableMessaging 状态机。
- **D4 renew 为调用方（租约调度方）策略**（P4-02 L-3 定案归位）：本卡在生产 wiring 落地 renew 调度（窗口 = TTL/2），载体与并发形态 GREEN 记录（EventLoop timer vs 独立线程），策略冻结于冻结参数节。
- **D5 ConnectionId 语义**：沿用 `ChatService.cpp connectionKey`（连接对象地址低 32 位）作为本地 claim 写入 Presence 的 connId 与本地匹配键；本地投递仍经 `SessionRegistry::lookupByUser`，epoch 校验用本地影子表（Gateway 本地 `(userId → SessionEpoch)`，claim 写入、release 清除；内部 seam，不进 Presence port）。
- **D6 允许写入清单**：见卡头（目录级 + 伴改文件列名：SessionDeliverySink、ProtocolCodec、ChatService、LocalOutboxRelay、RedisConn、main.cpp、两个 CMakeLists + **Config.hpp/.cpp**——后者为"config 新增 gateway 段"冻结决定（开卡待定 ⑤）的必然伴改，已登记；L1 自洽）。

## Interface / 可观察行为

```cpp
// chatserver/include/app/GatewayTransport.hpp（新建）
// 跨 Gateway 投递 port（ADR-0002、cluster-context-map §3）：把一条投递命令交给
// 目标 Gateway。本地路由（route.gatewayId == 本地 GatewayId）不应经本 port——
// 本地走 sink 直投（Gateway 感知 wrapper 内部短路）。transport 只按路由递送，
// 不承载消息真相；epoch 校验在目标侧（wrapper 收到跨节点投递后核验本地会话）。
struct GatewayDeliverResult {
    bool ok = false;
    bool staleEpoch = false;    // 目标侧核验发现 epoch 不匹配：已丢弃并触发目标侧重路由
    bool unreachable = false;   // 目标 Gateway 不可达（crash/分区/未注册）
    std::string error;          // 失败摘要（日志/指标，不含敏感 payload）
};
class GatewayTransport {
public:
    virtual ~GatewayTransport() = default;
    // route = Presence locate 返回的 DeliveryRoute；attempt = P3-07 冻结投递负载。
    // 不抛：全部失败收敛为结果字段。
    virtual GatewayDeliverResult deliver(const DeliveryRoute& route,
                                         const DeliveryAttempt& attempt) = 0;
};
```

- 可观察行为 ① deliver 前经 Presence 校验（无条目=离线、本地匹配=直投、跨节点=transport 路由、epoch 不匹配=丢弃+重路由）；② 旧 epoch 包不投递并触发重路由（重路由=本地重 claim/唤醒——返回 Closed 保留 Pending，由下次 sessionAvailable/claim 重新投递，**不产生第二套状态机**）；③ ACK 与 MessageId 语义与单机完全一致（同一 ledger 与 Delivery 状态机，本卡不新增 ACK/MessageId 定义）。
- Presence 生产接线可观察行为：login completion 在 `SessionRegistry.bind` 成功后 `claim`（生成新 epoch 原子覆盖，cluster-context-map §3）→ 提交 `sessionAvailableDelivery`；loginout/clientClose 时对绑定的 `(user, gateway, conn, epoch)` 做 compare-and-delete `release`（旧 epoch 被拒且条目不变，P4-01 契约）；renew 每 TTL/2 携带当前 epoch 执行（adapter 对旧 epoch renew 返回 NotEpoch——重登后旧调度 renew 被 fencing）。
- Redis down 降级（P4-00 冻结/ADR-0002）：新登录 claim 失败 → 登录暂停（不建 Presence 条目，不误投）；durable accept 继续；跨节点直投不可用（本地 locate 失败按离线处理，保留 Pending）。恢复后自动恢复，无需改库。
- **L3（协议澄清，2026-08-17）**：Redis down 登录暂停复用 `errno=1`（`ChatService.cpp` 登录路径 `"login temporarily unavailable, please retry!"`）——与既有通用登录失败共用 errno=1，不新增错误码。登记为协议澄清项（不改协议字段/错误码，见非目标"不改协议字段/错误码"），便于后续文档同步。

## 冻结参数（RED 前定案，不改动）

- **拓扑**：in-process GatewayTransport 单 Gateway 生产拓扑；GatewayId 生产默认从 config 注入（默认 1），测试注入不同值模拟多 Gateway。
- **deliver 前 locate 语义**：无 Presence 条目 = 离线——返回 Closed、保留 Pending 待登录 claim（行为与单机离线完全一致，不改）；有条目但 gatewayId 与本地不符 = 跨节点 → 经 transport 路由；有条目且 gatewayId 为本地但 epoch 与本地影子表不符 = 旧 epoch → **丢弃 + 重路由**（返回 Closed 保留 Pending，重路由=本地重 claim/唤醒，绝不按旧 epoch 继续投递）。
- **renew 策略**：窗口 = TTL/2（P4-02 L-3 调用方策略归位）；生产默认 TTL 30s（P4-02 冻结）→ renew 间隔 **15s**；renew 失败（Redis down）指数退避重试、不阻塞 accept/投递。
- **生产 relay 出口** = KafkaPublisher（topic `muduo-outbox`，P4-03 冻结命名）；**CF-1 处理 = publish 移出 relay 锁**（生产为真实 broker I/O，不接受锁内延迟为既定代价）。
- **P4-02 债务**：RedisConn RESP **有界化必须补齐**（命令/回复长度与嵌套深度上限）——本卡生产接线用 Redis 的前置条件；AUTH/TLS 因测试实例无密码登记延后（L-9，环境限制）。
- **消费侧生产 poll**：`KafkaEventConsumer`（host/port 生产 config，topic `muduo-outbox`、group `muduo-outbox-consumer`，fetchBatchLimit=100、poll deadline 冻结值）+ `WakeupProgressHandler`（P4-04 D1 延期项落地点）。
- **epoch 校验失败不破坏单机回归**：本卡以 P3 全部 process 回归（DomainCharacterization/DeliveryAck/BackpressureDelivery/ReconnectReplay/OutboxCrashRecovery 等）为单机行为零回归锚，Kafka-only 生产 relay 下必须全绿。
- 测试隔离：presence 用真实 Redis（`REDIS_TEST_*` 覆盖，沿用 P4-02 db=1）；broker 用 `muduo-test-*` topic 前缀（沿用 P4-03/P4-04）；真实 Redis/Kafka/MySQL 零 skip。

## RED

- 测试：`tests/unit/GatewayDeliveryContractTest.cpp`（新建；两个 in-process GatewayTransport 实例模拟 Alice/Bob 两 Gateway，共享 InMemory/真实 Redis Presence）——每场景公开 interface 失败测试：
  1. **无 Presence 条目时投递行为（离线不变）**：无条目 → sink Closed、无 socket 写入、Delivery 保留 Pending；登录 claim 后 sessionAvailable 恢复投递（与单机离线语义逐位一致）。
  2. **旧 epoch 收包丢弃+重路由**：路由携带旧 epoch（vs 本地影子表）→ 包被丢弃（零写入）、保留 Pending；随后 sessionAvailable 重 claim 后恰好投递一次（重路由=本地重 claim，无第二套状态机）。
