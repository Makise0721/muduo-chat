## 问题与证据（实测归因）

P5-03 只修实测热点（计划 §9.5）。P5-03A/P5-03C 两个 FAIL 共同归因：**durable 主成本 = accept 事务 3-4× SQL/msg + Conversation 行 FOR UPDATE 串行**。本卡选定台账候选「锁竞争缓解（accept 事务）」——针对主瓶颈本身，开卡先做改法评估：

- **accept 事务结构（MySQLMessageStore.cpp:624-763，`insertMessage` + `insertDelivery`）**：每个消息在同事务内执行（READ COMMITTED + START TRANSACTION）：
  1. `SELECT next_sequence FROM Conversation WHERE id=? FOR UPDATE`（:637，LockConversation——**同 Conversation accept 的串行点**，sequence 分配原子化，配合 `UNIQUE(conversation_id, sequence)` 兜底）；
  2. `UPDATE Conversation SET next_sequence=? WHERE id=?`（:648，AdvanceSequence）；
  3. `INSERT INTO ChatMessage(...)`（:667，InsertMessage——`(sender_id, client_message_id)` 唯一键幂等权威检查，1062 走回滚重读恢复）；
  4. `INSERT INTO OutboxEvent(...)`（:708，InsertOutboxEvent）；
  5. `INSERT INTO MessageDelivery(...)`（:747，InsertDelivery——每接收者一条，多条则逐条插、最后一条触发 COMMIT）；
  6. `COMMIT`。
  - 单接收者直发 = ~4 条数据 DML + 事务控制；P3-11/P5-02 归因的「3-4× SQL/msg」即此。
- **两个 FAIL 的归因链（本卡选择的直接证据）**：
  - P5-03C：批量 processed 标记把 accept 事务**之外**的每 scan 批 round-trip 从 N→1（省 ~99 条 UPDATE/5s），但同期 accept 路径 ~600-800 条 SQL 远超节省量 → 整体仅 +5.84%。**结论：主瓶颈在 accept 事务本身，而非其下游消费/标记路径**。
  - P5-03A：ACK 攒批因同步 HOL 语义冲突未接线，热路径不变 → 无收益。
  - 两个 FAIL 都落在 accept 事务**外部**；本卡把候选对准 accept 事务**内部**——即真正的 durable 主成本。
- **改法评估（本卡核心，见下节）**：对 accept 事务内部的两个可能减负方向逐一评估，结论均为超出单变量正确性可控范围。

## 改法评估（本卡核心，2026-08-25）

选定台账候选「锁竞争缓解（accept 事务）」，对候选内两个子改法逐一评估。评估原则 = 必须是台账候选内、**单变量最小改法**、且**正确性可控**（不改事务隔离 / 不改跨表原子性 / 不破坏 P3-04 冻结契约）。若超出则如实登记高风险/范围失控。

### 子改法 A：accept 事务内 SQL 语句数削减（合并可合并的 INSERT/UPDATE）

- 评估：事务内语句逐一审视是否可合并——
  - **Conversation `SELECT … FOR UPDATE` + `UPDATE` 读改写**：MySQL 无 `UPDATE … RETURNING`，sequence 的「读当前值→+1→写回」必须保持两步；合并成单条原子 `UPDATE … SET next_sequence=next_sequence+1` 后无法取回新 sequence 用于 ChatMessage/MessageDelivery 的 sequence 列 → 不成立。
  - **`INSERT ChatMessage` / `INSERT OutboxEvent` / `INSERT MessageDelivery`**：分属三张不同表（ChatMessage / OutboxEvent / MessageDelivery），且 ChatMessage 需 `mysql_insert_id()` 回读 id 供 OutboxEvent 与 MessageDelivery 引用 → **跨表依赖**，无法合并为单条多行 INSERT 而不改跨表原子性/改 schema（联合视图/触发器）——超出现有 schema 与事务语义范围。
  - **多接收者 `INSERT MessageDelivery` 逐条**：可合并为单条多行 `INSERT … VALUES (…),(…)`，但已按每接收者一条插且最后一条触发 COMMIT；reliable-direct 场景为**单接收者直发**，合并无收益（每条已是一条）。
  - 结论：accept 事务内的 ~4-5 条语句各自承担不可合并的语义职责（串行序列、消息行、outbox 行、投递行，含 id 回读依赖）。可合并空间主要落在 accept 事务**外部**（P5-03C 已做并证明收益面不足），事务**内部** SQL 削减与 P5-03C 属同一收益面——**与已 FAIL 的 P5-03C 重叠，预期同样收益面不足**，且真正可合并项需动跨表原子性/ schema。

### 子改法 B：Conversation 行锁粒度优化（`SELECT … FOR UPDATE` 串行）

- 评估：`SELECT … FOR UPDATE`（MySQLMessageStore.cpp:637）是**同 Conversation accept 的串行点**，保证 sequence 分配原子化（P3-04 明确建立并验证：配合 `UNIQUE(conversation_id, sequence)` 兜底）。优化方向（缩小锁范围 / 移除锁 / 改为无锁原子分配）必然触碰：
  - **sequence 分配原子性**：移除/缩小 FOR UPDATE 后，同 Conversation 并发 accept 可读到同一 next_sequence → sequence 竞争，只能靠 `UNIQUE(conversation_id, sequence)` 兜底 + 重试。兜底重试路径与 1062 恢复（:671-696）重叠但语义不同（Conversation 内 sequence 竞争 vs 幂等键竞争），需新增「sequence 冲突重试」状态机面——改动面超过 P5-03A 的攒批接线（后者已判接线复杂度过高）。
  - **P3-04 已验证的原子性/隔离承诺**：锁粒度优化属**改事务隔离/跨表原子性范畴**（Conversation 行锁是 accept 事务一致性的组成部分），违反本卡「禁止」节冻结契约与评估原则「不改事务隔离/跨表原子性」。
  - 结论：**正确性不可控**（需改 P3-04 已验证的序列分配原子性 + 新增重试状态机面），超出单变量范围。

### 评估结论：**改法评估为高风险/范围失控**

- 两个子改法均不满足「单变量最小改法 + 正确性可控」：
  - A（SQL 合并）与已 FAIL 的 P5-03C 收益面重叠（预期同样收益面不足），且真正可合并项需动跨表原子性/schema。
  - B（锁粒度优化）需改 P3-04 已验证的序列分配原子性 / 事务隔离，新增 sequence 竞争重试状态机面——正确性不可控。
- 结论：**如实登记「改法评估为高风险/范围失控」**，本卡不落地实现。
- **建议**：将 P5-03 循环收口——两个 FAIL（A/C）已共同归因 accept 事务为 durable 主瓶颈，而 accept 事务的减负改法均超单变量正确性可控范围；Buffer 分配复用（与 P5-04「Buffer 内存池化」spike 重叠，需 feature flag + 进入条件 = 分配次数/RSS 证明为主要瓶颈）**留 P5-04 spike**（计划 §9.6），不在 P5-03 单变量纪律下强推。此建议登记入台账，供 P5-03 循环收口决策。
