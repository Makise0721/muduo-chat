## Interface / 可观察行为

- `dbmigrate --to <version>`（默认全部）在空库和现有五表库上幂等升级；`dbmigrate status` 可查询版本、checksum、执行时间。
- 已应用版本的 migration 文件被修改后重跑 → fail-fast 报错，不改任何表。
- 并发执行：MySQL advisory lock（GET_LOCK/RELEASE_LOCK）保证同一数据库同时只有一个 runner 持锁；等锁语义 = 等待 `--lock-timeout` 秒（默认 10s），超时 fail-fast。
- 已存在表视为已应用（baseline 用 CREATE TABLE IF NOT EXISTS，旧五表库不报错、不重复建）。
- 测试 fixture 只调用 runner 建表；sql/chat.sql 与 baseline 的 DDL 漂移由 SchemaMigrationTest 捕获。
- 生产服务器（ChatServer）启动路径不调用 runner。

## 完成定义

- 同一 migration 不重复执行（重复运行 applied 为空、schema_migrations 每版本一行）。
- 改过的已执行文件因 checksum 不符而 fail-fast。
- 并发执行只有一个持锁者（两 runner 竞争：恰一个执行 0001）。
- 生产服务器启动不自动抢跑 migration（main.cpp 无迁移调用，测试固化）。

## 遗留（已知限制）

- 列级差异检测不在 P3-01 范围：runner 只做表级 `CREATE TABLE IF NOT EXISTS` 判定，列形漂移（如 password VARCHAR(80)）的库会被静默标记为已应用。SchemaMigrationTest.ColumnDriftLibraryMarkedApplied 固化现状行为；由 P3-03 故障测试（逐条违反唯一约束/FK）兜底。
- checksum 换行敏感性：SHA-256 按字节计算，CRLF/LF 混用会使已应用文件 checksum 不符而 fail-fast。仓库统一 LF（git 换行策略）下不构成问题，记录不修复。
