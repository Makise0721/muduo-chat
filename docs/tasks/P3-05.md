## 问题与证据

- 计划 §5 P3-05：登录成功后 Connection 绑定一个 User+generation；同一连接切换 User 被拒；消息/ACK 主体只来自 Session，不信任 JSON `id`。
- 现状（B-21，ChatService.cpp:213-223）：同一连接先后登录不同 User 均成功；`_userConnMap`（user→conn）只保证单用户单会话（B-08），不约束连接；oneChat/groupChat 的发送者身份来自 payload `id`（B-18/B-11/B-12），未登录也可发消息。
- P2-05 已提供 ChatApplication session generation（beginSessionAttempt/isSessionCurrent）防旧 completion 写重连后会话；P3-02 `SessionIdentity{userId,generation}` 为 ACK/lease 主体占位（P3-07 用 "uid:gen"）。
- message-reliability.md §1 Session identity 承诺 + §6 B-21 行（收紧，生效任务 P3-05）：发送者与 ACK 主体只来自已认证 Session。

## Interface / 可观察行为

- 登录成功 → 连接绑定 `BoundSession{userId,generation}`；同一连接二次登录（另一 User 或同 User）→ 拒绝（errno=2）；同一 User 已有其他活动连接 → 拒绝（errno=2，B-08 语义保留）。
- 未登录连接发 oneChat/groupChat → 明确拒绝（errno=1 + "please login first!"；记录：此前行为 = payload 转发/离线入队照常，B-25 只兜字段异常——新行为定为止步并报错）。
- payload `id` 存在且与 Session user 不符 → 拒绝（errno=1 + "invalid sender!"；不信任 payload）。
- 断开/登出 → 会话释放恰好一次（幂等）；旧 generation 登录 completion 不写新会话（既有 isSessionCurrent 机制 + registry 拒绝已绑定连接）。
- 好友（7）、建群（8）、入群（9）handler 保持 payload id 旧行为（回退保护，本卡记录边界）。

## 最小实现

- `chatserver/include/app/SessionRegistry.hpp` + `chatserver/src/app/SessionRegistry.cpp`：内部模块（进程内，P4 演进 Presence port）。`unordered_map<TcpConnectionPtr, BoundSession> byConnection_` + `unordered_map<int64_t, TcpConnectionPtr> byUser_` 双向，单 mutex 保护（多 Reactor：handler/completion 在主 loop 线程、close 回调在连接 loop 线程）。API：`bind(conn,userId,generation)->BindResult{Ok,ConnectionBusy,UserBusy}`（单锁内原子判定，顺带修掉旧 find+insert 两步竞态）、`unbind(conn)->释放的 userId（0=未绑定，幂等）`、`unbindUser(userId)->同上`、`lookupByConnection(conn,&out)`、`lookupByUser(userId)`、`snapshotConnections(userIds, excludeUserId)`（单锁快照，保持 groupChat 现状单锁语义）、`size()`。头文件前向声明 TcpConnection（不触碰 mymuduo API，chatserver_core 无需链接 mymuduo）。
- `ChatService.hpp`：`_userConnMap`/`_connMutex` 替换为 `SessionRegistry _sessions`。
- `ChatService.cpp`：login completion 改 `_sessions.bind`（UserBusy→errno=2 原文案；ConnectionBusy→errno=2 "this connection has already logged in!"）；loginout 改 `unbindUser(userid)`（payload id 语义与幂等保留）；clientCloseException 改 `unbind(conn)`（释放=userId≠0 才代次递增+离线落库）；oneChat/groupChat 入口先查 Session（未登录→errno=1 报错），payload id 不符→errno=1 拒绝，sender/跳过逻辑用 session.userId，在线转发/离线入队逻辑不变；长度检查（B-13）保持在会话检查之前。

## 对抗审查修复（Medium）：登录 bind 与断开竞态 → 会话泄漏

- 问题：login completion 的 `conn->connected()` 检查（ChatService.cpp:208）与 `_sessions.bind()`（:216）之间存在窗口——close 回调先被处理时 `unbind` 返回 0（尚未 bind），completion 后到把死连接绑定成功，close 回调永不再触发 → 会话泄漏，该用户被 B-08 永久锁死。原注释"防断线竞态锁死用户"名不副实。
- 修复（锁内活跃连接集合，无窗口）：
  - SessionRegistry 新增活跃连接集合：`addConnection(conn)`/`removeConnection(conn)`，与绑定映射同一把 mutex；元素为 `shared_ptr`（与 byConnection_/byUser_ 风格一致）。
  - `bind` 锁内先校验 conn 在活跃集合中，不在则拒绝新枚举值 `BindResult::ConnectionInactive`。
  - ChatService：onConnection 建立分支（ChatServer.cpp）调用 `addConnection`；clientCloseException 中 `removeConnection` 与 `unbind` 同一 close 回调内先后执行；login completion 保留 `connected()` 防御检查（注释修正为"防御性，权威判定在 bind"），新增 ConnectionInactive 分支（不建会话、restoreOfflineMessages、不响应）。
  - 锁内串行化保证：close 先于 bind → removeConnection 已执行 → bind 拒绝；bind 先于 close → bind 成功 → close 的 removeConnection+unbind 后到恰好释放。无窗口。
- 测试（SessionRegistryTest 补 5 用例，既有 11 用例前置 addConnection）：未登记 bind 拒绝、remove 后 bind 拒绝且用户不被占用、bind 后 remove+unbind 幂等清理、add→bind→unbind→重登→remove 全流程、bind 与 close 并发竞争无泄漏（500 连接 × 2 线程，断言 bind 成功 ⟺ unbind 恰好释放）。
- 验证：p3-05-fix-debug 聚焦 ctest（SessionRegistry/SessionApplication/DomainCharacterization）全绿；TSan 聚焦 SessionRegistryTest 10 轮全绿；`git diff --check` 通过。
