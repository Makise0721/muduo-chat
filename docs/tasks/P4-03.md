## Port 替换设计决定（开卡定案）

- `LocalOutboxRelay` 的 `MessageAcceptedConsumer& consumer_` 出口替换为 **`OutboxPublisher& publisher_`**（计划 §8："P3 LocalOutboxRelay 出口替换为 port；Recording 与 Kafka 两个 adapter；有界 batch/backoff"）。`MessageAcceptedConsumer` 类型退役。
- **本地 wakeup 成为 adapter**（cluster-context-map §4 第 3 行"出口替换为 OutboxPublisher port"的落地形态）：新建 `LocalWakeupPublisher : OutboxPublisher`，内部按 P3-09 语义从 `Message` 命令派生接收者（direct→directRecipient；group→成员快照，与 `LocalOutboxRelay::recipientsFor` 同构）并调 `ReliableMessaging::wakeupAccepted`，异常=该事件失败→不标 processed（语义与 P3-09 完全一致）。
- **以保持 P3 回归最小为准**：生产接线处 `ProtocolCodec.cpp` 的 `OutboxWakeupConsumer`（现实现 `MessageAcceptedConsumer::onAccepted`→`wakeupAccepted`）伴改为 `LocalWakeupPublisher`（同文件最小改，属 chatserver/src/app/ 允许范围）；`tests/unit/OutboxRelayTest.cpp` 的 `RecordingOutboxConsumer` 伴改为公共 `RecordingPublisher`（记录 publish 请求与逐事件结果，publish 请求保留事件+ConversationId，接收者断言经"LocalWakeupPublisher+记录"组合保留）。**若该伴改证明 churn 过大，回退为内联最小改动**（relay 保留 onAccepted 内联 + 新增 publish 出口），实际选择在 GREEN 记录。
- 事件种子与 schema 不改：`OutboxEvent.payload` 仍为 P3-04 冻结的命令快照 JSON，relay 只读、不删（findAccepted 幂等回读依赖）。

## Interface / 可观察行为

```cpp
// OutboxPublisher port：批量 publish MessageAccepted 事件，key=ConversationId（字符串化）。
// 同一事件重复 publish 安全（P4-04 消费者幂等；publish 本身不写数据库 → 不改变 Message/Delivery）。
struct OutboxPublishRequest {
    OutboxEvent event;             // relay 已 claim 的事件（含递增后 attemptCount）
    ConversationId conversationId; // Kafka 分区键（字符串化，见冻结参数）
    std::string topic;             // 目标 topic（测试注入 muduo-test- 前缀隔离）
};
enum class PublishFailure { None, Timeout, BrokerUnavailable, PayloadTooLarge, Other };
struct OutboxPublishOutcome {
    bool ok = false;
    PublishFailure failure = PublishFailure::Other;
    std::string error;             // 失败原因摘要（日志/指标，不含敏感 payload）
};
class OutboxPublisher {
public:
    virtual ~OutboxPublisher() = default;
    // 批量 publish（batch 有界，调用方不超上限）；返回逐事件结果（顺序与入参一致）。
    // deadlineMs 为整体操作软期限；超时/断连/broker 错误 → 对应事件失败，不抛、不写库。
    virtual std::vector<OutboxPublishOutcome> publish(
        const std::vector<OutboxPublishRequest>& batch, int64_t deadlineMs) = 0;
};
```

- relay 扫描改为：claim 一批 → 每事件 load Message（取 conversationId，缺 Message 判 poison 现状保留）→ `publisher.publish(batch, deadline)` → **逐事件结果 ok 才 `markOutboxProcessed`，失败保持未 processed、lease 到期重领**（P3-09 语义原样）。
- `KafkaPublisher`：真实 broker，每个事件一条 record，key=ConversationId 字符串；value=JSON 信封 `{"message_id":...,"conversation_id":...,"sequence":...,"event_type":"MessageAccepted","payload":<命令快照 JSON>}`（信封字段 P4-04 consumer 契约前冻结于此；`sequence` 供 P4-04 断言 partition 内顺序不倒退）。
- 故障分类：broker 不可达/连接超时 → `BrokerUnavailable`；操作超 deadline → `Timeout`；单条超限 → `PayloadTooLarge`；其余 → `Other`。全部不抛（逐事件失败，relay 继续同批后续）。
- **锁内 publish（CF-1）**：`publisher_.publish` 在 relay `mutex_` 内执行（`scanLocked`/`workerLoop` 持锁调用；`LocalOutboxRelay.cpp`）。broker 慢时 `scan`/`stop` 最多延迟 `publishDeadlineMs`（5000ms），有界无死锁（publish 不回头取 relay 锁）。P4-03 生产接线为 `LocalWakeupPublisher`，无 broker I/O、延迟近零；P4-05 接 `KafkaPublisher` 时须将 publish 移出锁（或接受该延迟为既定代价）。

## 冻结参数（RED 前定案，不改动）

- **publish batch 有界**：默认 100，沿用 `OutboxConfig.claimBatchSize`（P3-09 冻结）；KafkaPublisher 单批处理数与 relay claim 批一致，绝不超限。
- **key=ConversationId**（字符串化十进制，如 `"42"`）：同一 Conversation 事件进同一 partition（gateway-compose-topology.md 已约定 key=ConversationId）。
- **逐事件结果**：成功/失败分事件；失败不标 processed，由 lease 到期重领重试（重试=lease 到期重领，无 publisher 内部重试循环）。
- **broker timeout**：单次 publish 操作 deadline **5000ms**（构造参数可注入；fault 测试用更短值）。
- **测试隔离**：topic 前缀 `muduo-test-`（测试 topic `muduo-test-chat-outbox`，partitions=3）；生产 topic 名 `muduo-outbox`（本卡只冻结命名，不接生产 wiring）。

  1. **RecordingPublisher round-trip**：批量 publish → 逐事件结果全 ok；注入失败的批次逐事件 ok/fail 正确（失败不阻断同批）。
  2. **commit 后 publish 前 kill（未发布事件可重放）**：accept 写入 store 后不 publish（模拟进程在 publish 前崩溃）→ 新 publisher 重新 claim 并 publish，事件仍可重放（可被消费），无重复事件行。
  3. **publish 后 processed 前 kill（重放幂等）**：publish 成功但 markOutboxProcessed 前崩溃 → 重领后同事件再次 publish；断言 Kafka 中同 key 同 value 的 record 可重放，**Message/Delivery 状态不改变**（store 读 Message/Delivery 行数与内容不变——publish 不写库）。注（SP-2）：Kafka 路径以无 store 句柄+重放断言替代字面 store 行断言（publisher 契约测试无 store 面，行级不变断言归 OutboxRelay 回归）。
  4. **broker timeout（停 broker 或注入）**：停 Kafka（或注入慢/关闭端口）→ publish 逐事件失败（Timeout/BrokerUnavailable），relay 不标 processed、不崩溃；重启 broker 后重 publish 成功且已发布事件可消费。
  5. **重复 publish**：同一事件连续 publish 两次 → 两次逐事件结果均 ok；Message/Delivery 状态不变；Kafka 中为两条可重放 record（publisher 幂等由 P4-04 消费者保证，本卡断言 publisher 侧逐事件结果 + 不标 processed 语义）。
  6. **有界 batch/backoff**：事件量 > batch 上限 → 分轮 publish 每轮不超过上限；单次 publish 受 deadline 约束（无无界等待）。
