## 问题与证据（实测归因）

P5-03 只修实测热点（计划 §9.5）。本卡选定 **批量 ACK 合并（DELIVERY_ACK 攒批 UPDATE）**——计划候选台账**候选一**（批量 SQL/ACK 合并），开卡理由（实测归因证据）：

- **归因链条**：P5-02 gprof flat profile（`/mnt/d/muduo-chat-build/p5-02-gprof-profile.txt`）与基线报告（`docs/reports/performance/p5-baseline.md`）显示 reliable-direct 场景 msg/s=25.90、p50=751ms，reliable-group 16.00。P3-11/P3-13 已归因：**durable accept 的 DB 串行写是成本主因**（accept 事务 3-4×SQL，行锁 `SELECT ... FOR UPDATE` 串行化同 Conversation）。gprof 明确登记：**DB I/O wait 对本 gprof 不可见**（"DB I/O wait 对本 gprof 不可见（本负载 accept 事务 SQL/行锁等待为主要成本）"）——即 durable 路径的 CPU profile 只捕到 SQL 侧等待之外的间接成本，DB 串行写才是主瓶颈。
- **ACK 路径逐条 UPDATE**：`DeliveryCoordinator::acknowledge`（DeliveryCoordinator.hpp:43-87）对每个 `DELIVERY_ACK` 先 `deliveriesByMessage` 再 `store_.updateDelivery` 一次，即**一条 ACK = 一次独立 DB UPDATE 事务**（MySQLMessageStore.cpp:767 `UPDATE MessageDelivery SET ...`）。reliable-direct 是"在线接收者 + 客户端 ACK msgid 12"全路径，`reliable_acked` 与 `reliable_accepts` 同步增长——ACK 更新频率 = 消息率，每条 ACK 都是一次独立 round-trip UPDATE。
- **攒批可行性与归因直接可测**：ACK 更新是 `(message_id, recipient_id)` 主键上的幂等 UPDATE（state→Acknowledged），可攒批为单次多行 UPDATE（`WHERE (message_id,recipient_id) IN (...)` 或逐批提交），不改变 DELIVERY_ACK 协议语义。与候选台账其它项（Outbox lease 批量 claim、序列化拷贝消除、Buffer 复用、锁竞争缓解）相比，本项直接削减 durable 写路径的**每 ACK 一次 DB round-trip**，在 gprof 已证实的 DB 串行写主瓶颈归因下，是**最直接可测**的单变量。
- 结论：选候选一。若实测复测后门槛未达（本项削 DB round-trip 对整体 accept 串行成本影响不足以跨过显著阈值），循环协议第 6 步 revert 并将结论入台账，另选候选——不预设结果。

- **攒批不丢 ACK**：一批 N 条 ACK 全部落库为 Acknowledged，无遗漏（等价于逐条 N 次 UPDATE 的结果）。

- **崩溃恢复**：批中途失败（模拟 DB 故障/连接断）→ 已提交部分保留、未提交部分保持可重试，不出现部分 ACK 静默丢。

### 阶段 2 实现结果与「接线复杂度过高」登记（luna_worker，2026-08-24）

- **已实现**：`MessageStore::updateDeliveries(const std::vector<Delivery>&)`（MessageStore.hpp 默认回退逐条 `updateDelivery`，既有测试替身零伴改）；`InMemoryMessageStore` 逐条等价；`MySQLMessageStore` 单条多行 UPDATE（`SET state=?, acknowledged_at=CASE ... END WHERE (message_id,recipient_id) IN (...)`，per-row 秒对齐时间戳，prepared 绑定，批量键全为内部 BIGINT 无注入面）。**通过 RED 契约 6 语义（InMemory+MySQL 双 adapter）**。
- **DeliveryCoordinator 攒批接线：登记「接线复杂度过高」——未接线热路径**。理由（同步 HOL 语义冲突）：
  - `acknowledge`（DeliveryCoordinator.hpp:43-87）在 `store_.updateDelivery(*mine)` 后立即 `claimFor(acker)` 放行同 Conversation 下一 sequence。`claimFor` 经 `store_.deliveriesByRecipient` 读**同步**持久化状态（InMemory 即 store 本体；MySQL 为实时 SQL）。
  - 攒批延迟写（flush 窗口/阈值）会推迟 store 反映 Acknowledged → `claimFor` 读到旧 Pending/InFlight → HOL 不释放、已 ACK 消息被当作未确认而重投/重复。既有 `DeliveryCoordinatorTest`（HeadOfLineBlocksUntilAck 等）逐个断言 ACK 后立即放行 → 攒批延迟写必回归。
  - 保持同步 HOL 的正确攒批需在 Coordinator 引入写透本地 acknowledged 集合并改 `claimFor` 读取（新增状态机面、改动面失控、490 基线回归风险高），违反单变量/精准修改纪律。
  - 结论：仅实现批量方法（RED 契约通过），不接线热路径 → 热路径仍逐条 `updateDelivery` → 性能无收益（与复测一致）。
- **契约测试阶段 2 修正**（`BatchedAckContractTest.cpp`）：MySQL DATETIME(0) 秒精度无法 round-trip 非秒对齐时间戳 → 契约时间戳改秒对齐（`t0 + i*1000` 等）；`seedPendingDeliveries` 先 `getOrCreateConversation` 建 Conversation 行（MySQL `insertMessage` 需该行存在，否则 "conversation row missing"）。契约语义不变。
- **revert**：实现文件 `updateDeliveries` 已 `git checkout` 还原；热路径从未改动。RED 契约测试保留（下次候选的契约规格）。
