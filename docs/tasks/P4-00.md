## 问题与证据

现状是严格单机语义，没有任何跨节点概念（证据全部来自当前 checkout `main @ 6bfbf2e`）：

- **SessionRegistry 是进程内双向映射**：`SessionRegistry.hpp:22-24` 头注释"P3-05 进程内 SessionRegistry：深化 ChatService 的 _userConnMap…（P4 才演进为 PresenceDirectory port）"；`byConnection_/byUser_`（:83-86）只在进程内存中维护 connection↔session 一致性，不存在跨进程可见性。
- **LocalOutboxRelay 只唤醒本实例 coordinator**：`LocalOutboxRelay.hpp:65` `leaseOwner_` 为"本实例唯一 lease owner（并发 relay 竞争标识）"；P3-09 对抗审查 L 登记 #5（docs/tasks/P3-09.md:206-208）"多实例 wakeup 本地性：wakeupAccepted 只唤醒本实例 coordinator 的在线会话（activeByUser_）；接收者连到另一实例时本实例 wakeup 空操作，由该实例 relay 的周期扫描兜底"。即：跨实例投递只能靠数据库轮询，没有路由概念。
- **lease owner 含 boot id 但无 Gateway 概念**：`MySQLMessageStore.cpp:215-234` `encodeLeaseOwner` 编 `"uid:gen[:bootid]"`；`DeliveryCoordinator.hpp:31-37` 注释 bootId 为"该 ReliableMessaging 实例（进程）的启动标识"。boot id 是进程内重启用标识，不是集群寻址标识。
- **无 Presence 层、无跨节点路由**：全代码库与 CONTEXT.md 没有 Gateway/Presence/DeliveryRoute 定义；架构演进方案 §7 中 Redis Presence、Kafka Outbox、Gateway 定向投递均标注为 P4 目标。

集群词汇零定义证据（`rg -n 'GatewayId|ConnectionId|SessionEpoch|PresenceLease|DeliveryRoute' chatserver mymuduo CONTEXT.md`，exit 0）：

- `GatewayId`/`SessionEpoch`/`PresenceLease`/`DeliveryRoute`：**零命中**。
- `ConnectionId`：仅 3 处 executor lane-key 注释（`ChatService.cpp:15,24`、`SessionSerialExecutor.hpp:18`，作为 pre-login 任务 key 的非正式说法），无领域定义、无所有权语义，不进 CONTEXT.md。

## Interface / 可观察行为

本文档卡只产出可审阅的契约与拓扑描述，不产生运行时行为；后续 P4-01..P4-06 按契约落地（P4-01 PresenceDirectory interface、P4-02 Redis fencing、P4-03 Kafka Outbox、P4-04 幂等 consumer、P4-05 Gateway 定向投递、P4-06 三节点 chaos）。

冻结目标（RED 前定案，供后续审阅）：

- 领域词汇与唯一含义（GatewayId/ConnectionId/SessionEpoch/PresenceLease/DeliveryRoute，见 ADR-0002 与 context map）。
- MySQL 继续是 Message 真相源；Redis 只保存可过期路由状态；Kafka 只传递可重放事件（演进方案 §3 不变式）。
- 连接归属 Gateway；Session 跨 Gateway 唯一（同一 User 全集群至多一个活动 Session）。
- Presence 只含路由与 epoch，不含消息真相。
- 每个依赖故障（快速重登/旧 Gateway 延迟 release/网络分区/Redis down/Gateway kill/broker 重放）对 accept/login/delivery 有唯一预期降级结果。
