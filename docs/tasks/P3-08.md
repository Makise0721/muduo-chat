## 问题与证据

- 计划 §5 P3-08：ACK timeout 后相同 MessageId 重投；重连立即唤醒 pending；offline 不消耗快速重试额度；到 expiresAt 后进入 Expired；acked/expired 按独立 retention 清理。ReliableMessaging 内部 timer 驱动的 bounded batch scheduler，指数 backoff+jitter 与可控 Clock；参数从 config 注入，测试不依赖 sleep。完成定义：当前 `takeOffline` 读删流程已不在新路径；重试任务有界、退出可 drain/cancel；过期可查询而非静默丢失。
- spec §3 状态机：`InFlight --> Pending: ACK timeout / 断开`、`Pending/InFlight --> Expired: retention deadline`、`Acknowledged/Expired --> [*]: retention cleanup`。spec §4 故障点：ACK 丢失 → ACK timeout 后回 Pending，按 backoff 重投同一 MessageId，attempt_count+1；重连 → 新 Session 立即 claim 自己名下 Pending（不等 backoff，offline 不消耗快速重试额度），不 claim 他人 Delivery；过期 → 进入 Expired，不静默删除，指标与管理查询可见，仅 audited cleanup 清理。spec §7 未定值冻结清单：ack timeout/backoff cap、message retention/cleanup batch 在本任务 RED 前记录，不承诺具体数值于规范。
- 现状（P3-07 后）：没有 ACK timeout，没有重投 timer/backoff；lease 到期只能在下次 sessionAvailable/accept/ACK 触发的 claimFor 时被动重领，无独立扫描推进；没有 `Pending/InFlight → Expired` 状态转移；没有 acked/expired retention cleanup；ACK/sessionClosed 的 executor submit rejection 未处理（P3-07 遗留，P3-07 卡"本轮未闭合项"：ACK/sessionClosed 保持状态，按 P3-08 的事件触发/timeout 恢复范围处理）。

## 冻结参数（RED 前定案）

以下初值在生产默认、测试注入范围与依据上一次性定案；测试小值不得成为生产默认；全部经 config 注入，不经代码常量硬编码。

| 参数 | 生产默认 | 测试注入范围 | 依据 / 备注 |
|--------|----------|--------------|-------------|
| ack_timeout_ms | **30000**（30s） | 100..5000 | 给在线接收端足够的展示+ACK 时间（spec §4 ACK 丢失行靠重投收敛，非无限等待）；30s 显著高于正常 ACK RTT 且低于 message_retention 7d，避免未确认消息在 Expired 前被过早重投；P3-12 负载报告后按实测 ACK p99 调整 |
| retry backoff base | **1000ms** | 随注入（测试建议 10..200ms） | 首次重投前等待；指数退避起点 |
| retry backoff cap | **60000ms** | 随注入 | 长期 unacked 重投间隔上限，防止高频风暴；须明显小于 message_retention |
| backoff 乘子 | **2** | 2（固定） | 指数退避；每次 attempt 后 next = min(base * 2^(attempt-1), cap) 加 jitter；生产默认 2（config 可覆盖；测试固定 2） |
| jitter | **±20%（均匀分布）** | 同生产公式，参数化 | 打散同批重投，避免 herd 效应；均匀分布，非确定性必须经可控 Clock 覆盖 |
| offline 快速重试额度 | **offline 期间不消耗** | 同生产语义 | 重连立即 claim 自己名下的 Pending（spec §4 重连行），不等待 backoff、不把离线时长算进重试额度 |
| message_retention | **7 天**（expiresAt = created_at + retention） | 秒/分钟级 | 未确认消息进入 Expired 的期限；spec §4 过期行：已接受消息在 retention 内最终 ACK 或保持可查询 Pending/Expired |
| acked_retention | **1 天** | 秒/分钟级 | Acknowledged 行保留可查询期，之后 audited cleanup |
| expired_retention | **1 天** | 秒/分钟级 | Expired 行 audited cleanup 前的可查询期 |
| cleanup batch | **100 行/轮** | 注入 | 每轮清理行数上限，有界幂等 |
| cleanup 周期 | **60s** | 注入 | scheduler 周期扫描间隔 |
| scheduler | **单 worker 定时线程 + 有界批次（batch 上限 500 行/轮）**；队列/扫描有界；stop/drain/cancel 有界 | 注入 | 计划 §3 深模块内部 seam、§5 P3-08 与 §10 停止条件：无无界扫描/队列；timer 驱动不用 fixed sleep 测试 |

## Interface / 可观察行为

- ACK timeout 后同一 MessageId 重投：attempt_count+1、last_sent_at 更新、next_attempt_at 按 backoff+jitter 推进；同 `(recipient, conversation)` 前序未确认时不投后续 sequence（HOL 保持）。
- 重连立即唤醒自己 Pending：新 Session 上线 claim 名下 Pending，不等 backoff、不消耗快速重试额度；不 claim 他人 Delivery（P3-07 既有 fencing 保持）。
- Expired 可查询：SQL（`state=Expired` 行可定位 expires_at/attempt_count）与指标快照可见，不静默删除；进入 Expired 的 Message 不再重投。
- acked/expired 独立 retention 清理：acked_retention 管 Acknowledged 行、expired_retention 管 Expired 行，各自 batch 有界、周期执行、重复运行幂等。
- scheduler 优雅退出：stop 走有界 drain/cancel，无悬挂任务、无无界等待。
- 暴露入口：ReliableMessaging 现 interface 不变（accept/acknowledge/sessionAvailable/sessionClosed/start/stop(Deadline)），retry/expire/cleanup 全部隐藏在模块内部；新增内部有界 scheduler 与可控 Clock seam（沿用 Clock.hpp UnixEpochClock）。

### 1. ACK/sessionClosed executor submit rejection 恢复策略（P3-07 carryover 闭合）

**冻结决定**（与 P3-07 已闭合的 sessionAvailable/pressure resume 拒绝策略对称，不扩大到其它 executor 拒绝路径）：

- **ACK submit 被拒（RejectedFull/RejectedShutdown）= 丢弃**。等价 ACK 丢失：P3-08 ack-timeout 对同一 MessageId 重投即恢复路径，客户端按 message_id 去重（at-least-once 契约）。不主动重试，不自建恢复队列。
- **sessionClosed submit 被拒 = 不新增立即动作**。名下 InFlight 保持，由 scheduler/lease 在到期后回退 Pending（等待重连 claim）——无 sessionClosed 时 `claimFor` 的 lease 到期路径（`InFlight && leaseUntilMs <= now`）与 `runRetryScan` 已覆盖该恢复。

代码仅在 `ChatService.cpp` 的 `deliveryAck`/`loginout`/`clientCloseException` 三处提交点补显式注释锁定策略，不改行为（忽略返回即丢弃/no-op）。

**测试锁定**（现有测试已覆盖恢复路径，无需新增，补显式说明）：
- 丢 ACK → 超时重投同 message_id：`DeliveryRetryTest.AckTimeoutRetriesSameMessageId`（R1，域级无 acknowledge 调用即等价 ACK 丢失）。
- 无 sessionClosed 时 lease 到期后 InFlight 可重领：`DeliveryCoordinatorTest.AckLossHoldsUntilLeaseExpiry`（同 generation、全程无 sessionClosed、越过 lease 后 sessionAvailable 重领）。

### 2. 跨进程重启 lease owner 碰撞（generation 重置）

**RED**：`DeliveryCoordinatorTest.RestartWithSameGenerationReclaimsStaleLease`——模拟 kill/restart（新 coordinator 实例 + 同一 uid:gen + 未到期 lease + InFlight 行），期望新实例 `sessionAvailable` 立即重领；现状因 owner 字符串相同（MySQL `lease_owner` 编 `"uid:gen"`，重启后 generation 重置为同值）而不重领，HOL 卡到 lease 到期（RED 输出 attempts()==1，期望 2）。

**根因**：P3-07 C fencing 判定 `d.leaseOwner != session` 只看 (uid, gen)；跨进程后同 (uid, gen) 视为自己的在途 lease，不回收。

**最小修复**：lease owner 加入进程实例标识。
- `DomainTypes.hpp Delivery.leaseBootId`（uint64，claim 时与 leaseOwner 一并写入并持久化）。
- `ReliableMessaging` 构造时生成 boot id（pid ^ steady-clock 时刻 ^ 每进程构造计数；同进程多次构造必不同），传给 `DeliveryCoordinator`。
- `DeliveryCoordinator::sessionAvailable` fencing 改为 `!(d.leaseOwner == session && d.leaseBootId == bootId_)`：同进程同代匹配仍精确（自己的在途不回收），跨进程 owner 必不同（立即回收）。
- MySQL `lease_owner` 列编 `"uid:gen:bootid"`（VARCHAR(64) 足够，最坏约 52 字符）；`decodeLeaseOwner` 兼容旧格式 `"uid:gen"`（bootId=0，遗留行必然不等 → 安全方向立即回收）。

不破坏 P3-07 gen fencing 测试（同进程同代/跨代/迟到 ACK/迟到 available 语义不变）；真实 MySQL round-trip 由 `MySqlReliableMessagingDb.*`（12 项）与 `ReliableMessagingContractTest`（MySQL 侧 4 项）全绿锁定。
