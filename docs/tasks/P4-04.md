## 设计决定（开卡定案）

- **D1 consumer 形态——port + Kafka adapter，不做 consumer group 协议**：
  - port 两面：`OutboxEventConsumer`（驱动面：同步 `poll(deadlineMs)`，单调用方线程完成 fetch→handle→dead-letter→commit，无内部后台线程——生产接线由 P4-05 决定）+ `DeliveryProgressHandler`（处理面：幂等推进既有 Delivery）。in-process 处理 adapter = `WakeupProgressHandler`（复用 P3-09 seam）；Kafka adapter = `KafkaEventConsumer`（扩展内置 wire 客户端：Metadata + ListOffsets + Fetch + OffsetFetch + OffsetCommit）。
  - **manual partition assign（assign topic 全部分区）+ offset 存 Kafka（simple-consumer commit）**，不实现 FindCoordinator/JoinGroup/SyncGroup/Heartbeat。理由：单 broker 开发拓扑（P4-03 冻结，PLAINTEXT 回环 9092）下 group coordinator 即该 broker，JoinGroup/SyncGroup（member 元数据/分配策略/心跳租约）复杂度与单消费者收益不成比；RED ②"rebalance 恢复"以**"consumer 重启接管全部分区、从已提交 offset 恢复"**语义如实覆盖（manual assign 下分区所有权不迁移，只有重启接管；同 group 多实例并行消费不在本卡契约——登记为 P4-06 chaos/生产化前扩展项）。
  - wire 复用：从 `KafkaPublisher.cpp` 匿名命名空间提取共享原语到 `app/KafkaWire.hpp/.cpp`（TcpClient、请求帧/响应帧、ByteWriter/ByteReader、varint、magic-2 record batch 编解码），KafkaPublisher.cpp 伴改为 include 替换（行为零变化，P4-03 回归作证）；Fetch 参考 KafkaTestConsumer 已实证形态（Metadata v1/ListOffsets v1/Fetch v4/CreateTopics/DeleteTopics）；OffsetFetch/OffsetCommit **无先例**，RED 前按待定①实测校准。若提取证明 churn 过大，回退为 adapter 自包含 wire 副本（同 KafkaTestConsumer 先例），GREEN 记录实际选择（默认：提取）。
- **D2 幂等处理语义——只推进不重建，重复=no-op 成功，乱序=不破坏+dead-letter**：
  - `WakeupProgressHandler::handle`：`store.findMessage(messageId)` → 缺行 dead-letter（`message_missing`，见下）→ `outboxRecipientsFor(msg->command)` → `rm.wakeupAccepted(recipients)`。**绝不调 insertMessage/insertDelivery/accept**；状态机只前进由 claimFor fencing 保证（有效 lease 的 InFlight 不重领、Acknowledged 短路）。
  - 重复事件（同 message_id 重投）：`DuplicateNoOp`——无操作成功，Delivery 行/attemptCount 不变（claimFor 对已 InFlight(有效 lease)/Acknowledged 的行为）。
  - 乱序事件：consumer 按 partition 消费序维护 per-conversation lastSeen sequence；`sequence < lastSeen` → 不推进 + dead-letter `sequence_regression`；`sequence == lastSeen` 且 message_id 相同 → 重复 no-op；message_id 不同 → dead-letter `sequence_conflict`（DB `UNIQUE(conversation_id,sequence)` 下理论不可达，防御断言）。Kafka 分区保序（key=ConversationId 同分区，P4-03 冻结）本身保证新鲜追加不倒退；该断言防御 publish 侧重放/手工注入乱序。lastSeen 生命周期：per-conversation 内存态，重启即重建，重启窗口内 sequence_regression 防御失效由 fencing + DB UNIQUE 兜底；GREEN 实现不得做持久化。
  - **规则序修订（H 级修复，审查后 2026-08-17 补记；原规则/理由/新规则）**：
    - **原规则**（KafkaEventConsumer.cpp 处置管线）：`sequence < lastSeen[conv]` → `sequence_regression` dead-letter 的检查排在"同 message_id 重复投递"判定之前——同一批内同 conversation 的 seq1/seq2 两条 record 均已处置（lastSeen 推进到 seq2）后，批未提交（commit 前 kill）重放时，seq1（已 Advanced）会先命中 `seq1 < lastSeen(seq2)` 被误判 `sequence_regression` 落 dead-letter，而非按 D2"重复事件 = DuplicateNoOp"处理。
    - **理由**：重复判定必须以 (conversationId, messageId) 键控而非仅以 sequence 键控；lastSeen 只能表达"该 conversation 见到的最大 seq + 其 messageId"，无法表达"seq1 这条 messageId 已被处置过"。未提交批重放（L-2/RED ②/⑨ 场景）下这是确定的误判，产生虚假 dead-letter 行。
    - **新规则**：处置管线新增规则 3——同 `(conversationId, messageId)` 已见（先前处置成功 Advanced/DuplicateNoOp，记入 per-conversation seenMessages 内存集合）→ `DuplicateNoOp`，**置于 `sequence < lastSeen` 回归规则之前**；死信/乱序规则顺延（poison→unknown_type→已见重放→regression→conflict→handler）。实现：`KafkaEventConsumer::Impl` 新增 `std::map<uint64_t,std::set<uint64_t>> seenMessages`（per-conversation messageId 集合，处置成功即 insert，重启重建不持久化）；测试新增 `InMemoryConsumeFixture.ReplayBatchWithMultipleRecordsPerConversationIsDuplicateNoOp`（RED→GREEN，见 §GREEN 执行记录末）。
  - 缺 Message 行：立即 dead-letter `message_missing`，不无限重试。理由：单共享 MySQL 拓扑中 accept 事务先于 outbox claim/publish 提交（P3-09 顺序），缺行即不可恢复不一致；无限重试会把 dead-letter-able 的分区头卡死（head-of-line 阻塞比可查询落库更糟）。
  - store 瞬时异常（wakeupAccepted/updateDelivery 抛出，如 MySQL timeout）：**不 dead-letter、offset 不提交**，poll 返回失败，下轮重放——at-least-once 投递 + 幂等处理收敛（绝不宣称 exactly-once）。
- **D3 dead-letter 存储——MySQL 新表 KafkaDeadLetter（0003 migration）**，不复用发布侧 poison 机制：`markOutboxPoisoned` 按 outbox 事件 id 键控、语义属 relay 发布侧；消费侧 poison 需 Kafka record 定位 + 原始 bytes。经 `MessageStore` port 扩展（默认 no-op 沿 P3-09 惯例，既有测试替身零伴改），InMemory/MySQL 双 adapter 契约双跑。`UNIQUE(topic, partition_id, kafka_offset)` 使 kill-前已落库的事件重放时不双插（幂等）。可查询性：`deadLetters(limit)` 谓词 + 测试直接 SQL 断言。
- **D4 冻结参数**：见冻结参数节（topic/group/批上限/poll/commit 时机与 deadline/env，全部 RED 前定案）。
- **D5 允许写入清单**：见卡头"允许写入"（目录级，新文件+伴改文件列名）。
- **D6 Commit 消息**：`feat(cluster): consume outbox events idempotently`（编排者给定，与 `feat(cluster): publish outbox events to kafka` 对仗、仓库风格一致）。

// chatserver/include/app/OutboxEventConsumer.hpp
// 一条从 broker 拉到的 MessageAccepted 事件（信封字段 P4-03 冻结，不改一字段）。
struct ConsumedOutboxRecord {
    std::string topic;
    int32_t partition = 0;
    int64_t offset = 0;
    uint64_t messageId = 0;
    uint64_t conversationId = 0;
    uint64_t sequence = 0;
    std::string eventType;   // 只接受 "MessageAccepted"
    std::string payload;     // 命令快照 JSON（P3-04 冻结编码）
};
enum class ConsumeDisposition {
    Advanced,       // 推进了既有 Delivery（幂等 wakeup 生效，Pending→InFlight 等）
    DuplicateNoOp,  // 同 message_id 重复投递：无操作成功（行/attemptCount 不变）
    DeadLettered,   // poison/乱序/缺行：已落 KafkaDeadLetter（可查询），未推进状态
};
// 处理面 port：只推进既有 Delivery，绝不重建（D2）。
class DeliveryProgressHandler {
public:
    virtual ~DeliveryProgressHandler() = default;
    virtual ConsumeDisposition handle(const ConsumedOutboxRecord& record) = 0;
};
// 驱动面 port：同步 poll（fetch → 逐事件 handle → poison/乱序 dead-letter 落库
// → 全部终态后才 commit offset）。store 异常/broker 故障 → 本批不提交、返回
// 失败（下轮重放，at-least-once）；poll 本身不抛。
struct OutboxConsumeResult {
    std::vector<ConsumedOutboxRecord> records;     // 本批拉到的事件
    std::vector<ConsumeDisposition> dispositions;  // 与 records 一一对应
    bool processed = false;        // 本批是否全部到达终态（含 dead-letter 落库）
    bool offsetCommitted = false;  // 仅在 processed 后才可能 true（时序断言观察点）
    std::map<int32_t, int64_t> committedThrough;   // partition → 已提交 offset+1
    bool brokerOk = true;          // false = 本轮 broker 故障（无任何副作用）
};
class OutboxEventConsumer {
public:
    virtual ~OutboxEventConsumer() = default;
    virtual OutboxConsumeResult poll(int64_t deadlineMs) = 0;
};
// Kafka adapter（构造注入：host/port/topic/groupId/fetchBatchLimit/deadlineMs，
// 同 KafkaPublisher 形态；另含 preCommitHook 适配器具体 seam——P4-01 injectFailure

// 启动恢复：OffsetFetch 读回已提交 offset；无提交历史 → ListOffsets(-2) earliest。
class KafkaEventConsumer : public OutboxEventConsumer { /* ... */ };
// in-process 处理 adapter：findMessage → 缺行 dead-letter → outboxRecipientsFor
// （LocalWakeupPublisher.hpp 公开 inline，复用）→ ReliableMessaging::wakeupAccepted。
class WakeupProgressHandler : public DeliveryProgressHandler { /* ... */ };

## RED

- 测试：`tests/unit/OutboxConsumerContractTest.cpp`（新建），每场景穿过公开 interface + **真实 Kafka**（127.0.0.1:9092，topic `muduo-test-consume-outbox`），**不 skip**（broker 不可用即测试失败）：
  1. **round-trip 只推进不重建**：经 store+accept 建 Message/Delivery（recipient 离线）→ KafkaPublisher 发布事件 → consumer poll → `Advanced`，Delivery Pending→InFlight（sink 观察）、Message/Delivery 行数不变（只推进不重建）；offset 提交。
  2. **处理后 offset 提交前 kill**：事件已 handle（sink 已见 attempt）→ preCommitHook 注入抛出（模拟 commit 前 kill）→ offset 未提交 → 新 consumer（同 group）OffsetFetch 回退 → 重放同一事件 → `DuplicateNoOp`、attemptCount 不重复加、dead-letter 无重复行（UNIQUE 幂等）——重启不产生重复副作用。
  3. **重启接管全部分区恢复**（manual assign 的 rebalance 语义）：实例 A 消费提交到 offset X → 销毁 A → 新实例 B 同 group 从 X+1 继续、不重放已提交区间；broker 侧 `__consumer_offsets` 与 B 的 committedThrough 一致——断言手段：以第三实例 OffsetFetch 读回核验（或 `kafka-consumer-groups --describe` 对照）。
  4. **重复事件**：同 message_id 连投两条 record → 第二条 `DuplicateNoOp`，Delivery 行/attemptCount/state 不变（重放幂等）。
  5. **乱序事件**：同 conversation 手工注入 sequence 倒退 record（同 key 同 partition）→ 不推进 + dead-letter `sequence_regression`（SQL/deadLetters 可查询）→ 后续正常 sequence 事件继续推进（不 head-of-line 卡死）。
  6. **poison 事件**：坏 payload JSON / 未知 event_type / 缺 Message 行 → 各自 reason dead-letter、**可查询**（deadLetters 谓词 + 直接 SQL 断言行存在），绝不只日志丢弃；offset 在 dead-letter 落库后提交（后续事件不阻塞）。
  7. **offset 提交时序断言**：RecordingHandler 记录 handle 顺序 + preCommitHook 记录 commit 时刻 → 断言全部 handle（含 dead-letter 落库）先于 commit；commit 传输失败注入 → 本轮不提交、下轮重放安全（重放结果与 2 一致）。
  8. **broker 故障**：停 broker（或 BlackholeServer 注入）→ poll 返回 brokerOk=false、无副作用、不崩溃；重启后恢复消费。
  9. **handler 抛出（store 瞬时异常面）**：注入对某 record 抛出的 handler（前缀成功+目标抛出）→ poll 不抛；该批不提交 offset（broker 停留上一提交点）；下轮 poll 重放同批：前缀记录 `DuplicateNoOp`（lastSeen 批中止保留 + claimFor fencing）、目标 `Advanced`；重放成功后无重复副作用（幂等由 DuplicateNoOp/UNIQUE 兜底）；broker offset 一次推进到位（L-2 升格 RED 场景钉死合同；L-3 lastSeen"处置成功时更新、批中止保留已更新值"语义一并钉死——测试文件头契约块处置顺序第 9 条对应）。
