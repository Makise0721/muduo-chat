## 问题与证据

`TcpConnection.cc:68`（跨线程 send）：

```cpp
loop_->runInLoop(std::bind(&TcpConnection::sendInLoop, this, message.data(), message.size()));
```

- 捕获裸 `this`：连接可能在回调执行前被销毁 → UAF；
- 捕获 `message.data()`/`size()`：调用者字符串在 `send()` 返回后可能失效 → UAF。

`TcpConnection.cc:136`（跨线程 shutdown）：

```cpp
loop_->runInLoop(std::bind(&TcpConnection::shutdownInLoop, this));
```

同样捕获裸 `this`。

## Interface / 可观察行为

- 保持现有 `void send` 业务语义（P0 不引入 SendResult）；
- 跨线程发送必须拥有 payload，不依赖调用者生命周期；
- 排队回调持有连接到执行结束（shared_ptr）；
- shutdown/close 幂等，callback 不重复；
- 所有 Channel 操作仍在所属 EventLoop。

## 非目标

- 不实现背压、Timer、通用 Executor（P1）；
- 不改变 loop 线程内 send 的直调路径语义。

预期失败：跨线程 send 后立即释放 payload/连接 → 队列回调执行时读已释放内存 →
ASan heap-use-after-free；哨兵保证回调必然执行（FIFO），不靠 sleep 猜时序。

实际证据（2026-08-09，WSL Ubuntu，ASan 构建 /tmp/muduo-chat-build/asan）：

```
$ ctest --test-dir /tmp/muduo-chat-build/asan -R CrossThread --output-on-failure
  -> Test #22 CrossThreadSendOwnsPayloadAndConnection ***Failed
     ERROR: AddressSanitizer: heap-use-after-free ... in write            (payload 悬空)
     ERROR: AddressSanitizer: heap-use-after-free ... in std::atomic<int>::operator int (对象悬空)
  -> Test #23 CrossThreadShutdownOwnsConnection ***Failed
     ERROR: AddressSanitizer: heap-use-after-free ... in unique_ptr<Channel>::_M_ptr (shutdown 悬空)
  -> Test #24 交错测试 Passed（payload/连接均存活时无 UAF）
```

测试采用阻塞器模式（queueInLoop 阻塞回调 + promise 进出信号）保证循环线程在处理
send/shutdown 回调前被确定性暂停，消除时序竞态；哨兵（FIFO）确保回调必然执行。

## 最小实现

- `send(std::string message)` 按值拥有数据；
- 跨线程路径：`runInLoop(bind(static_cast<SendInLoop>(&sendInLoop), shared_from_this(), std::move(message)))`
  （bind 重载需要显式转型）；
- 新增私有转发重载 `sendInLoop(std::string)`，仅调用期内使用数据；
- `shutdown()` 排队时捕获 `shared_from_this()`。
