## 问题与证据

- 计划 §5 P3-09：未处理 OutboxEvent 可用 lease 批量 claim；本地 relay 唤醒 DeliveryCoordinator；成功后标记 processed，失败/崩溃后可重领。RED 含 commit 后 relay 前 kill、处理后 processed 标记前 kill、重复处理、两个 relay 竞争、poison event；当前只有表记录而没有消费者。完成定义：周期扫描保证 lost wakeup 后仍推进；relay 队列/批次有界；未处理/重试/poison 指标可见；P4 能替换 relay 出口而不改 accept 事务。提交 `feat(message): relay durable outbox events locally`。
- 路线（handoff §11 P3-09）：有界批量 claim 的 `LocalOutboxRelay` + Recording adapter；周期扫描保证 lost wakeup 恢复；同一 MessageAccepted 重放只产生幂等 wakeup；处理成功后才标 processed。非目标：不创建 Kafka port/consumer，不进入 P4。验证 `OutboxRelay|OutboxCrashRecovery` until-fail:10；真实 MySQL 两 relay 竞争与 kill/restart；未处理/重试/poison 可见；Debug/ASan/TSan/Release。stop：队列/批次无界、poison 静默丢弃、commit 与 outbox 不原子。
- 现状（P3-04 起）：`MySQLMessageStore::accept` 在同一事务内 `INSERT INTO OutboxEvent(aggregate_message_id, event_type, payload) VALUES(?, 'MessageAccepted', ?)`（chatserver/src/app/MySQLMessageStore.cpp 事务步骤 `fire(Step::InsertOutboxEvent)`），`available_at` 取默认 CURRENT_TIMESTAMP，`lease_owner`/`lease_until` 为 NULL，`attempt_count=0`、`processed_at=NULL`（schema §3.6）。**没有任何消费者**：无 relay、无 lease claim、无 processed 标记，未处理事件只增不减。`loadMessage`/`findAccepted` 的幂等键回读依赖 `ChatMessage m JOIN OutboxEvent o ON o.aggregate_message_id=m.id AND o.event_type='MessageAccepted'`（同文件 loadMessage），因此 **relay 只能标 processed、不得删除行**——行删除会破坏 findAccepted 的幂等回读；行的生命周期（含清理）不在本卡范围（P3-10 观察窗口 / P4 publisher 出口接管）。
- 现状（P3-08 后）：accept 提交后由 `ReliableMessaging::accept` 内的 `notifyAcceptedBestEffort` 直接调用 `coordinator_.onAccepted(recipients)` 做在线 claim；该 wakeup 是 best-effort（异常吞掉），且进程崩溃时完全丢失——lost wakeup 恢复（周期扫描 outbox 并重放 MessageAccepted）正是本卡职责。重放幂等依赖既有 DeliveryCoordinator claimFor 的 fencing（已 InFlight/Acknowledged 不重复 claim、HOL 保持）与 P3-08 scheduler 的幂等。
- 基线事实：HEAD=7fe8ada（P3-08 原子提交，P3-08 卡 VERIFIED）；docs/README.md 与 implementation-sop.md 路由已指向 P3-09 待开卡，本卡开卡时最小同步为当前活动卡。

## 冻结参数（RED 前定案）

relay 需要自己的周期扫描与有界批量 claim。以下初值在生产默认、测试注入范围与依据上一次性定案；测试小值不得成为生产默认；全部经 config 注入，不经代码常量硬编码（沿用 P3-08 RetryConfig 注入模式）。

| 参数 | 生产默认 | 测试注入范围 | 依据 / 备注 |
|--------|----------|--------------|-------------|
| outbox claim batch | **100 事件/轮** | 注入（建议 1..10） | 每轮最多 claim/处理的事件数，与 P3-08 retryBatchLimit/cleanupBatch 同模式；LIMIT 有界 |
| outbox scan interval | **5000ms** | 注入（建议 10..200ms） | 周期扫描保证 lost wakeup 恢复（进程重启 / best-effort wakeup 丢失后仍推进）；timer 驱动，测试不用 fixed sleep |
| outbox claim lease 时长 | **30000ms** | 注入 | claim 时写 `lease_owner/lease_until`（沿用 Delivery lease 语义，schema §3.6 列已存在）；lease 到期可重领，崩溃无清理路径依赖到期重领 |
| attempt_count 语义 | 每次 claim+1，不设自动放弃上限 | 同生产 | 重试由 lease 到期驱动持续直至成功或被人工处理；poison 为可查询谓词而非自动丢弃（见 Interface） |

以上全部为**初值**，正式值由 P3-12 fault matrix/负载报告（outbox lag、claim 冲突率）支撑后调整；任何调整先改本卡再动代码。

## Interface / 可观察行为

- 未处理 OutboxEvent 可**有界批量 claim**：lease_owner/lease_until/attempt_count 语义沿用 Delivery lease（schema §3.6 列已存在，无需 migration）；每次 claim 写 owner+lease_until、attempt_count+1；claim 到期的行可被重领。
- **周期扫描**保证 lost wakeup 恢复：relay 单 worker 定时扫描未处理（或 lease 已到期）事件，即使进程在 accept 提交后、wakeup 前崩溃，重启后事件仍可被 claim 并重放。
- 同一 MessageAccepted 事件**重复处理只产生幂等 wakeup**：重放调用 DeliveryCoordinator 的接受通知（对事件 payload 派生出的接收者），claimFor 对已 InFlight/Acknowledged 行 fencing，不产生重复 DeliveryAttempt；不重新创建 Message/Delivery。
- **处理成功后才标 processed**：`processed_at` 只在处理成功（wakeup 完成、无异常）后写入；失败/崩溃保持未 processed，lease 到期后可重领。
- 未处理/重试/poison 可查询：SQL 谓词能定位未处理（processed_at NULL）、重试中（attempt_count>0 / lease 占用）与 poison（payload 不可解析且未 processed）的事件，不静默丢弃（P3-12 再接管为指标）。
- 暴露入口：`LocalOutboxRelay` 模块 + 可控 Clock seam（沿用 Clock.hpp）+ RecordingOutbox adapter（测试）；MessageStore 增 outbox 相关 port 方法，InMemory/MySQL 双 adapter 实现。
- 现有 ReliableMessaging accept/acknowledge/sessionAvailable/sessionClosed/start/stop 外部 interface 不变；relay 与 accept 事务解耦（relay 只消费 accept 事务已提交的 OutboxEvent）。

## 非目标

- **不创建 Kafka port/consumer**（P4-04 才做 OutboxPublisher port；P4-03 才替换 relay 出口为 port）。relay 出口就是本卡的 LocalOutboxRelay。
- 不做 legacy backfill（P3-10）、keyed executor（P3-11）、指标系统（P3-12，仅保证未处理/重试/poison 可查询为指标预留）。
- 不改 schema/migration（OutboxEvent 六表契约已含所需列，schema §3.6；约束 `UNIQUE(event_type, aggregate_message_id)` 已锁幂等）；不改冻结协议 msgid 11/12/13 与 errno 101..107。
- 不删除已处理 OutboxEvent 行（findAccepted 幂等回读 JOIN 依赖它；行生命周期清理归 P3-10/P4 出口）。
- 不承诺 exactly-once（at-least-once + 幂等 wakeup）；不重写 P3-07/P3-08 DeliveryCoordinator 与 scheduler 语义。

## RED 计划

每个场景先写公开 interface 的失败测试（穿过 LocalOutboxRelay/MessageStore port/Clock/Recording adapter/config 注入，不读私有容器、不依赖固定 sleep），再实现最小代码。测试命名具体在 RED 时定，当前清单如下：

1. **commit 后 relay 前 kill**：OutboxCrashRecoveryTest（+ 真实 MySQL process）——accept 事务已提交但 relay 从未消费，事件仍在（未 processed、lease 为 NULL），新 relay 可 claim。
2. **处理后 processed 标记前 kill**：OutboxCrashRecoveryTest——wakeup 完成但 processed_at 写入前进程退出，重启后同一事件可被重领；重放只产生幂等 wakeup（不重复投递）。
3. **重复处理同事件**：OutboxRelayTest——同 MessageAccepted 事件被处理两次（手工重放/重领），第二次 wakeup 幂等：不新增 DeliveryAttempt、不新建 Message/Delivery。
4. **两个 relay 竞争**：OutboxRelayTest（+ 真实 MySQL process）——两个 relay 同时扫描，同一事件仅一者得 lease；败者不 claim、不处理。
5. **lease 到期重领**：OutboxRelayTest——处理进程"崩溃"（无 processed 标记）后 lease 过期，另一 relay/新实例可重领并处理。
6. **lost wakeup 恢复（周期扫描）**：OutboxRelayTest——best-effort wakeup 丢失后不依赖 accept 路径，周期扫描仍 claim 并唤醒 coordinator（在线接收者收到投递）。
7. **poison event**：OutboxRelayTest——payload 不可解析/处理抛异常的事件不静默丢弃、可查询（poison 谓词命中）、不影响同批后续事件处理。
8. **批次/队列有界**：OutboxRelayTest——超量事件只按 batch 上限分批处理；单 worker 队列/扫描有界；stop 有界 drain/cancel（无悬挂任务、无无界等待）。

预期失败：现状无 relay、无 MessageStore outbox port 方法（`claimOutbox...`/`markProcessed...` 不存在）、无 processed 标记路径，第 1..8 项目标在现状下因接口不存在而 compile 失败，或（若仅以 store 行状态断言）因无 claim/processed 行为而无从通过。

## 最小实现

- **MessageStore port 扩展**：新增 outbox 相关方法（如 `claimOutboxBatch(nowMs, leaseOwner, leaseUntilMs, limit)`、`markOutboxProcessed(id)`、未处理/重试/poison 查询谓词），InMemory 与 MySQL 双 adapter 实现（LIMIT 有界）；MySQL 侧 lease_owner/lease_until/attempt_count/processed_at 写随 schema §3.6 既有列，不经 migration。
- **LocalOutboxRelay**：有界批量 claim + 单 worker 线程 + 周期扫描（可控 Clock，timer 驱动不用 fixed sleep）+ stop 有界 drain/cancel；claim 写 lease_owner/lease_until/attempt_count+1；处理成功才写 processed_at；异常不静默丢弃（poison 可查询，不影响后续批次）。
- **幂等 wakeup**：重放 MessageAccepted → 对 payload 派生接收者触发 coordinator 接受通知（如 `onAccepted(recipients)`）；依赖 P3-08 scheduler 幂等 + DeliveryCoordinator claimFor fencing，同一事件重放只产生幂等 wakeup、不重复投递。
- **Recording adapter**：测试用 RecordingOutbox adapter（记录 claim/processed 轨迹），生产走 MySQL。
- **最小接线**：ReliableMessaging/ProtocolCodec/ChatService 仅做启动/停止 relay 与 config 注入的最少改动，不改 accept 事务（commit 与 outbox 保持原子，不破坏 durable acceptance）。
- 冻结参数经 config 注入（默认=上表生产默认），测试用小值注入，两者分离。

### M 修复轮（2026-08-14，luna_worker）——wakeup 异常不再被吞，瞬时存储故障不消费事件

审查 M（Spec）：`ReliableMessaging::wakeupAccepted` 走 `notifyAcceptedBestEffort` 吞全部
异常 → 生产 `OutboxWakeupConsumer::onAccepted` 永不抛 → `LocalOutboxRelay` 消费时判处理

wakeup 恢复"（周期扫描）双双失效。方向安全但语义空洞。修复与证据：

- **RED**：`OutboxCrashRecoveryTest.WakeupStoreFailureKeepsEventUnprocessed`（新增，公开
  `MessageStore` 装饰器 `ThrowOnceOnWakeupUpdateStore`，照 ContractTest 的
  `ThrowOnceOnUpdateStore` 模式在 `updateDelivery` 注入一次异常，默认不武装）——场景：
