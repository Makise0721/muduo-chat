## 问题与证据

- 计划 §5 P3-06：direct/group 命令携带 ClientMessageId 与 typed content；`MESSAGE_ACCEPTED` 返回 ClientMessageId、MessageId、ConversationId、ConversationSequence 和 `duplicate`；两个协议 adapter 把 JSON 转换成 `SendMessageCommand`；ChatService 只负责 codec/session/Reply 映射，Message 接受进入 executor 后调用 ReliableMessaging；旧 msgid 6/10 缺 ClientMessageId 时生成 legacy identity 并标记 implicit-ack 模式，内部仍走同一 ledger，不保留第二套 storeOffline 实现，指标单独计数。
- 现状（P2 行为，B-11/B-12/B-17/B-13/B-18/B-19）：oneChat/groupChat 在线成员直接转发原始 Command（ChatService.cpp:325-455），离线入 `storeOfflineMessage`，回复=回显原 JSON + `errno` 0/1/2（CONTEXT.md Errno）；非成员发群聊与成员查询失败仍 `errno=0`；超长按整条序列化 payload>500 拒绝（B-13，VARCHAR(500) 驱动）。
- spec §7 协议最小集合：可靠发送命令含 `client_message_id`；`MESSAGE_ACCEPTED` 五字段；DELIVERY_ACK 含 `message_id`，UserId 从 Session 获取。spec §2.5：新 msgid 不得占用 1..10（B-22 锁定 ChatService.hpp:25-36），整数编码在 P3-06 protocol golden 一次冻结。
- P3-04 契约缺口衔接：MySQL adapter 的 `MessageStoreError`（DependencyBusy/IdempotencyConflict/TooManyRecipients/NotFound/Storage）经异常传递，本任务在应用层映射为 `AcceptOutcome` 与稳定错误响应；`SendMessageCommand.members` 由命令携带——本任务上层校验成员资格并提供快照，MySQLMessageStore 只消费快照不查成员表（P3-04 卡注释）。
- P3-04 自投递锁定：群快照含 sender 时 sender 也有 Delivery 行（SenderInMembersGetsOwnDeliveryRow），是否过滤由本任务决定（见冻结决策表）。

## Interface / 可观察行为

- direct/group 命令携带 `client_message_id`（ASCII 1..64，缺失→legacy 判定，非法→InvalidClientMessageId）与 content（≤16KB，冻结值见决策表）；v1/v2 双 codec 对称（spec §2 协议表）。
- `MESSAGE_ACCEPTED` 返回 `client_message_id`、`message_id`、`conversation_id`、`sequence`、`duplicate`；只在该事务提交后发出；同键重试返回原值（spec §2.2）。
- 稳定错误响应：不存在用户/群、非群成员、超限 content、幂等冲突、DB busy 各有唯一编码（冻结决策表 §2），同 key 重试返回同一错误；legacy 客户端收到通用失败。
- 重试语义：accept 回复丢失后同 command 重试得到同 identity（duplicate=true）；legacy 无幂等保证（legacy identity 不稳定，spec §5.1）。

| 4. 错误编码形式 | **errno 扩展（1xx 稳定错误码）+ errmsg 字符串双通道**；错误响应字段 `{msgid:13, errno, errmsg, client_message_id(可解析时回显)}` | v2 客户端按 errno 机器判别、errmsg 可读；legacy 客户端只认 0/1/2（CONTEXT.md Errno），新码对 legacy 一律映射 errno=1 通用失败 |
| 5. 错误码数值（建议，golden 定稿） | 101=NotConversationMember、102=TooManyRecipients、103=IdempotencyConflict、104=DependencyBusy、105=ContentTooLong、106=NotFound（任务卡暂名 TargetNotFound，golden 与 spec §2.4 对齐用 NotFound）、107=InvalidClientMessageId | spec §2.4 表逐条；105/107 为 codec/应用层错误（accept 前拒绝），不来自 MessageStoreError 映射；101/102/103/104 由 StoreErrorKind 映射（P3-04 缺口闭合） |
| 6. content 上限 | **16KB**（content 字段 UTF-8 字节，超限→errno=105） | spec §6 B-13 相关：500 字节旧上限废止（新路径不再写 OfflineMessage VARCHAR(500)）；schema ChatMessage.content MEDIUMBLOB=16MB 是列容量不是业务规则（计划 §6）；可调但实现时在 codec 记录实际判定口径 |
| 7. typed content | **保持最简：`content` 为字符串，无类型字段** | spec §2.1/§7 无 typed 定义；P3-02 `SendMessageCommand.content` 已为字符串；P3 不引入 content_type，未来扩展走协议演进（新字段可选、缺失视为 text） |
| 8. 群成员快照 | 上层（ChatService 切片）在 executor 内查成员表：发送者不是成员→101；成员列表填 `SendMessageCommand.members`（保序），MySQLMessageStore 只消费快照 | P3-04 卡衔接；B-18 收紧在应用层落地；群查询失败→DependencyBusy（B-19 收紧，不再 errno=0） |
| 9. 群自投递 | **保持现状：快照含 sender 时 sender 也有 Delivery 行，不过滤** | P3-04 锁定 SenderInMembersGetsOwnDeliveryRow；过滤是行为变化，本卡冻结现状；如需过滤另提决策 |
| 10. legacy 响应格式 | **建议：旧格式兼容——回显原 Command + `errno=0`（成功）/`errno=1`（失败）+ errmsg，不向 legacy 客户端发送 MESSAGE_ACCEPTED** | 风险：legacy 客户端收不到 message_id/conversation_id/sequence，无法按 MessageId 去重→重试可能重复展示（legacy identity 跨重启/重试不稳定，无幂等保证，能力差异）；implicit-ack（P3-07）使断线窗口内消息不重投。替代方案（一律 MESSAGE_ACCEPTED）破坏旧客户端硬编码 msgid 回显匹配，否决。**阶段 B 实现时确认**（P3-10 cutover 观察窗口后由部署决策宣布 legacy 退出日期，spec §5.1） |
| 11. legacy identity | 在线：`legacy:<UserId>:<进程内单调计数>`；迁移行 `legacy:<offline_id>` 属 P3-10 | spec §5.1；跨重启/重试不稳定是明确能力差异；legacy-mode count 指标本卡先标记计数，正式指标 P3-12 |
