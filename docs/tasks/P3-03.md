## 物理 schema 决策（本任务冻结，约束未削弱）

- 全部新表 `ENGINE=InnoDB DEFAULT CHARSET=utf8`（0001 风格）；FK 沿用 0001 的 `ON DELETE CASCADE`。
- `client_message_id VARCHAR(64) CHARACTER SET ascii COLLATE ascii_bin NOT NULL`：ASCII 1..64 上界由领域层 `ClientMessageId` 校验（P3-02，InvalidClientMessageId 错误在 P3-06）承担，MySQL 5.7/8.0 CHECK 不强制；DB 层用 ascii 字符集防非 ASCII，`ascii_bin` 排序规则落地大小写敏感；DB 严格 sql_mode（STRICT_TRANS_TABLES）下超长报 1406，非严格部署会截断——文档化为已知限制（docs/specs/schema.md §4）。
- `MessageDelivery.state TINYINT NOT NULL DEFAULT 0`（编码 0=Pending 等由 adapter 隐藏，本任务不定语义）；`attempt_count INT NOT NULL DEFAULT 0`；lease/时间列 `DATETIME NULL`；`lease_owner VARCHAR(64) NULL`。
- `Conversation.kind ENUM('DIRECT','GROUP') NOT NULL`；`next_sequence BIGINT UNSIGNED NOT NULL DEFAULT 0`；`Conversation.id/ChatMessage.id/OutboxEvent.id BIGINT UNSIGNED AUTO_INCREMENT`。
- `OutboxEvent.event_type VARCHAR(64) NOT NULL`、`payload MEDIUMBLOB NOT NULL`（P4 可加事件类型，ENUM 不改）。
- FK 类型匹配（MySQL 要求同型）：user/sender/recipient/group 相关列 `INT`（引用 User.id/AllGroup.id 的 INT），conversation/message 相关列 `BIGINT UNSIGNED`。
- 0002 语句拆分契约：6 条 CREATE TABLE，每条以 `;` 结尾，字符串字面量无 `;`（runner splitStatements 约定）；全部 `CREATE TABLE IF NOT EXISTS`（中断重跑幂等）。

## 最小实现

- `sql/migrations/0002_expand.sql`：只新增六张表（见物理 schema 决策）；不改、不删 `OfflineMessage`；runner 零改动（多文件支持已在 P3-01）。
- `tests/unit/SchemaMigrationTest.cpp`：5 个用例的断言从"0001 只应用一次/6 表"演进为"0001+0002/12 表"——共享迁移目录加入 0002 是既有测试语义的自然变化，否则聚焦闸门无法通过；断言集合精确（含新表名）。
- 测试文件落地时对 MySQL 8.0 事实的修正（ReliableMessageSchemaTest，原稿未经验证）：① `column_key` 只标记索引首列——`client_message_id`（复合 UNIQUE 第二列）为空键而非 MUL；② 复合 PK 全部成员均为 PRI——`MessageDelivery.recipient_id` 为 PRI 而非 MUL；③ `foreignKeySet` 过滤旧五表（information_schema 返回全库 15 条 FK，断言对象是六新表 10 条）；④ `InterruptedMigrationRerunConverges` 先落 0001 再手刷 0002 前 3 条——MySQL 8.0 拒绝引用尚不存在表的 FK（error 1824），空库直接刷 0002 不可能成功，且"0001 已应用、0002 中断"才是真实中断场景（部分应用后 8 表 → 重跑 12 表）；⑤ 去掉 `SET SESSION max_allowed_packet`（MySQL 8.0 该变量 SESSION 只读，服务器默认 64MB 已覆盖 33.5MB 查询）；⑥ `makeConn` 改为就地连接（MySQL 不可拷贝，隐式浅拷贝会双重 close）。
