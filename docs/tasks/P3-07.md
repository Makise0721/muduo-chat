## 问题与证据

- 计划 §5 P3-07：Session 上线后 claim 自己的 Pending Delivery；socket 准入成功转 InFlight；客户端按 MessageId ACK；重复/迟到/他人 ACK 幂等且不越权；每个 `(recipient, conversation)` 一条 InFlight 上限（HOL，ACK 后放行下一 sequence）。
- spec §3 网络联动：只有 `TcpConnection::SendOutcome.disposition` 已接受才记录 attempt；PauseProducer 时等待 low-water 回调不自旋；Closed 时保留 Pending；write completion 不直接产生 ACK。
- P3-02 遗留登记：`DeliverySink::deliver` 现返回 void，P3-07 需返回结果通道；claim 先置 InFlight 与 spec §3（准入才转 InFlight）冲突，需调整 claim→deliver→状态更新顺序。
- 现状（P3-06 后）：accept 路径只入 ledger，无任何投递（在线收不到、登录不补投）；`sessionAvailable/sessionClosed` 无调用方；早期 `wiring()` 单例用 NoopDeliverySink 占位，现已由可晚绑定且未绑定 fail-closed 的 forwarding adapter 替代；P3-05 SessionRegistry 已提供 conn→user 双向查找（sink 寻址基础）。

## 冻结决定（RED 前定案）

| 决策项 | 冻结值 | 依据 / 备注 |
|--------|--------|-------------|
| 1. 投递消息格式 | **旧格式扩展**：原命令 msgid（direct=6/group=10）+ 原字段（id=发送者、toid/groupid）+ 服务器字段 `{message_id, conversation_id, sequence}` + content；不新增 msgid | 最简：msgid 复用既有 6/10（B-22 锁定，不新增冻结值）；legacy 客户端忽略附加字段照常展示（与旧离线补投同形状）；v2 客户端按 message_id 去重/ACK。实现位置 SessionDeliverySink.cpp |
| 2. legacy implicit-ack | legacy 消息（client_message_id 以 `legacy:` 前缀，spec §5.1）在 socket 准入（disposition=Accepted 且无背压）后**立即**标记 Acknowledged，不进入 ACK timeout/重投循环；Paused/Closed 不视为准入，保留 Pending | spec §5.1「socket 准入后即标记 Acknowledged」+ 本卡决策 3 的 AcceptedPaused 不记 attempt 规则；同 conversation 的 legacy 链式连续放行（登录一次补投全部 legacy Pending，等价旧离线补投语义） |
| 3. SessionDeliverySink 映射 | `Accepted+Normal` → Accepted（记 attempt）；`Accepted+PauseProducer` / `WouldBlock` → Paused（不记、保留 Pending、暂停该 Session）；`Closed`/`TooLarge` → Closed（不记、保留 Pending，不暂停） | 任务书原文「Accepted→记 attempt；AcceptedPaused/WouldBlock/Closed→不记、保留 Pending」；Paused 时消息已在输出缓冲（客户端会收到），resume 后重投产生重复由客户端按 MessageId 去重（at-least-once，spec §4 ACK 丢失行） |
| 4. 在线投递触发 | accept 提交后立即 claim **在线**接收者（coordinator 维护 activeByUser 活动会话表）；离线保持 Pending 待登录 claim | 否则在线收不到消息（P3-06 已退役在线转发）；P3-02 契约不受影响（契约测试 accept 时无活动会话） |
| 5. claim 顺序 | 先 deliver 后落状态：sink 返回 Accepted 才写 InFlight+lease+attemptCount+1；拒绝则不改行 | spec §3「Pending → InFlight: lease + socket 准入」；claim token = lease_owner/lease_until（准入成功才签发） |
| 6. 背压暂停范围 | paused 为 Session 级集合；暂停中 sessionAvailable/accept 触发/ACK 放行的 claimFor 全部短路；仅 low-water 回调（resume）解除 | 「PauseProducer 时等待 low-water 回调不自旋」；会话级（同连接所有 conversation 同进退） |
| 7. ACK 无回执 | DELIVERY_ACK（msgid=12，`{message_id}`，UserId 取 Session）处理为静默：不回复、不重投、重复/迟到/他人 ACK 幂等且不越权 | spec §2.3/§4 故障点 4/5；协议未定义 ACK-ACK |

## Interface / 可观察行为

- `DeliverySink::deliver` 返回 `DeliverDisposition{Accepted, Paused, Closed}`（port 签名变更，P3-02 登记落地）。
- `ReliableMessaging` 新增 `resume(session)`（low-water 恢复，P3-07 内部 seam；其余 P3-02 接口不变，acknowledge/sessionAvailable/sessionClosed 委托给内部 DeliveryCoordinator）。
- `DeliveryCoordinator`（claim/lease/ACK/背压暂停/活动会话/legacy implicit-ack 状态机）。
- ProtocolCodec 新增自由函数：`registerDeliverySink(DeliverySink*)`、`acknowledgeDelivery(uid, gen, messageId)`、`sessionAvailableDelivery(uid, gen)`、`sessionClosedDelivery(uid, gen)`、`resumeDelivery(uid, gen)`（executor worker 串行驱动，ReliableMessaging 单一调用者约束保持）。
- ChatService：登录 completion 后 claim（B-09 补投演进）；close/登出提交 sessionClosed；DELIVERY_ACK handler（Session 取 ACK 主体）；登录连接注册 low-water pressure 回调（weak 捕获防循环引用）。
- 可观察：在线收消息（accept 即投递）；登录收 Pending；ACK 放行下一 sequence；断线 Pending 保留、重连重投（同 message_id，客户端去重）；legacy 投递即确认不重投。

### 独立 RED：accept 提交后 updateDelivery 故障

- 测试：`tests/unit/ReliableMessagingContractTest.cpp` 的
  `ReliableMessagingContractTest.PostCommitDeliveryFailureKeepsAcceptAndRetryClaimsPending`；
  通过公开 `MessageStore` interface 的 `ThrowOnceOnUpdateStore` decorator，使首次
  `updateDelivery` 抛出一次异常，不读取 adapter 私有容器。
- 场景：先以 `sessionAvailable(bob)` 建立在线接收者，再 accept direct 消息；这会在
  `insertDelivery` 已完成 durable commit 后进入 `onAccepted`/`claimFor`，由 sink 先接受
  attempt，再在落 `InFlight` 时注入 `updateDelivery` 异常。随后用同一
  `(sender, client_message_id)` 重试，要求返回原 MessageId/`duplicate=true` 且再次触发
  Pending 在线投递。
- 命令：
  `wsl.exe -d Ubuntu -- bash -lc 'set -euo pipefail; cmake --build /mnt/d/muduo-chat-build/p3-07-debug --target ReliableMessagingContractTest -j2; /mnt/d/muduo-chat-build/p3-07-debug/bin/ReliableMessagingContractTest --gtest_filter=ReliableMessagingContractTest.PostCommitDeliveryFailureKeepsAcceptAndRetryClaimsPending'`
- 结果：构建退出 **0**；测试退出 **1**。精确失败为：`line 353 Value of: threw Actual: true Expected: false injected updateDelivery failure`；同次运行还显示 `first.ok` 为 false（期望 true）、durable `message_id=1` 与未赋值的 `first.messageId=0` 不一致、retry identity 不一致，以及 attempts 保持 **1**（期望 **2**）。

### SessionDeliveryArmer 生命周期契约审查（仅接口/测试收口）

- Finding：`SessionDeliveryArmer` 是 `ChatService` 自有的 internal seam，不是提供
  generic self-lifetime safety 的 callback 工具。`armer`、`SessionRegistry` 与每个
  `TcpConnection` owner `EventLoop` 必须存活到所有 queued `arm/clear` functor 及
  pressure callback 完成；`weak_ptr<TcpConnection>` 只避免延长 connection，不保护
  armer、registry 或 owner loop。销毁前，已 arm 的每个 Session 必须在其 expected
  generation 上 `clearSessionDelivery`，并在 owner loop 上通过 barrier/drain。
- 生产所有权证据：`ChatService::instance()` 返回 function-static `ChatService`；
  `_deliveryArmer` 与 `_deliverySink` 是该对象成员，`_sessions` 先于它们声明，故
  armer/registry 由同一 function-static service 持有。生产 close/logout 在
  `unbind/removeConnection` 前调用 `clearSessionDelivery`；`main.cpp` 的 shutdown
  顺序证据为 `STOP_ACCEPT → DRAINED/DRAIN_TIMEOUT → EXECUTOR_SHUTDOWN →
  POOL_SHUTDOWN → QUIT_LOOPS → EXITED`。当前顺序保持 armer/registry 及 owner loop
  存活至网络 drain；`shutdown-order` 只证明该全局标记顺序，不把它扩展为 generic
  armer lifetime/destructor guarantee。生产 function-static/member 析构不替代
  显式 clear/barrier 契约。
- 测试收口：`ArmInstallsCallbackBeforeAvailableSubmit`、
  `StaleExpectedSessionCannotSubmitResume`、`ReLoginReplacesOldPressureCallback`
  与 `RejectedAvailableClosesCurrentExpectedOnce` 现在都在结束前对当前 expected
  generation 调用 `clearSessionDelivery`，再用真实 owner-loop `real.run` no-op
  barrier；已有 `ClearPreventsResumeForExpectedSession` 与
  `RejectedResumeAfterReloginDoesNotCloseNewSession` 保留同样 barrier。每次 clear
  均使用对应 generation，不使用 sleep，也不掩盖原断言。
- 该 finding 未改变 production `.cpp`、ChatService shutdown 或 CMake；现有行为基线
  保持 GREEN。后续需以显式 ASan+UBSan（`detect_stack_use_after_return=1`）、Debug
  重复测试与 `shutdown-order` process 证据复审本契约；本节不宣称完整 P3-07 已
  `VERIFIED`。
