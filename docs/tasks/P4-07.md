### H 级发现（登记）

- **假设缺陷**：`ConsumerConfig.groupId` 原冻结默认 `muduo-outbox-consumer` 全 Gateway 共享 →
  在"managed consumer group（rebalance）"语义下同一 group 每个事件被唯一消费者消费，跨节点在线
  接收者的本地 wakeup 事件可能被错误 Gateway 消费（其 coordinator 无该用户 active，事件空转）→
  在线跨节点投递退化到接收方 scheduler 周期扫描（ack_timeout 粒度，生产 30s）或重连才送达。
- **实测复核结论**：本实现为 simple consumer（`KafkaEventConsumer`，manual assign 全分区 +
  `consumer_group_generation_id=-1` + OffsetFetch/OffsetCommit 按 group 存储 + **内存 cursor**
  只在启动时初始化一次），故**稳态双进程下每个 consumer 各自消费全部事件**，共享 group 并不会
  让事件被唯一消费者消费——假设的"共享 group→在线跨节点 >10s 空转"在 fresh-topic 双进程实测中
  **未复现**（共享 0.08s vs 派生 0.05s，见下方数字表）。
- **伪 RED 溯源**：首轮 derived 观测到 10.02s 未达、重连后 0.04s 补投，根因是**共享 Kafka topic
  历史积压**（`muduo-outbox` 已有 12242 条事件；共享组 committed=12241 跳过积压，而派生组为
  全新 group 从 offset 0 重放 12k 积压后才追上新事件）——测试卫生问题，非共享 group 语义缺陷。
  修复后测试脚本支持每轮独立 `P407_TOPIC` 后两轮均 ≤0.12s。
- **修复作为加固依然正当**：每 Gateway 独立 consumer group = 独立 offset/去重状态隔离，消除跨
  进程同 group OffsetCommit 竞态（重启恢复各自从本组 committed 重放全部未消费事件，不因他组
  commit 推进而跳事件）；若未来迁移到 managed consumer group，则恰好防住发现所述的
  "每事件唯一消费者" 缺陷。方向安全、无行为回退。

### 最小修复决策（冻结）

- **数据面不变**：不引入 v2 TCP RPC；投递仍走共享 MySQL Pending → 接收方 Gateway claim 的
  durable 路径（`MySQLMessageStore` claimFor + lease fencing，P3-07/P4-05 冻结语义）。
- **wakeup 面**：`GatewayConfig::effectiveConsumerGroupId()`——显式 `group_id` 非空优先，
  否则按 Gateway 派生 `muduo-outbox-consumer-<gatewayId>`；每 Gateway 独立消费组、各自消费
  全部 outbox 事件并只 wake 本地 active 用户（coordinator fencing 幂等），恢复本地 wakeup 语义。

- **ConfigTest 伴改**：显式优先（`GatewaySectionOverridesKeepsFrozenDefaults`）、按 id 派生

### 镜像策略与探测（策略②：docker import 自制最小 rootfs）

- 探测：`docker images` 本地空（无 ubuntu/debian 等 base）；`docker pull hello-world` 25s 超时
  （Docker Hub registry 网络受限，与卡头环境变更节一致）；`curl https://registry-1.docker.io/v2/`
  connect timed out；`curl http://archive.ubuntu.com` 200（apt 可达）。用户无 root/sudo
  （sudo 需密码），无法 debootstrap/apt 拉 base。
- 决策：策略② 卷/自制 rootfs 分支——`docker/ build_rootfs.sh` 从 WSL2 宿主 Ubuntu 24.04
  （与构建环境同 glibc ABI）拷贝 `ChatServer/dbmigrate` + `libmymuduo.so` + 全部 ldd 动态依赖
  （libmysqlclient.so.21/libstdc++/libssl/libcrypto/libz/libzstd/libnss 等），`docker import`
  为本地镜像 `chat-m4-rootfs:latest`（68.7MB）。容器内实测 ChatServer 可加载运行（能连 MySQL，
  证明 ELF 与依赖解析正常）。
- 共享依赖复用宿主：三 Gateway 均 `network_mode: host`，直接访问宿主 MySQL 127.0.0.1:3306 /
  Redis 127.0.0.1:6379 / Kafka 127.0.0.1:9092（本环境宿主依赖只监听 127.0.0.1，容器无法经
  bridge 访问宿主回环；host 网络是"复用宿主依赖"约束下的最小等价方案——对文档 §3"单一 bridge
  chatnet"的等价落地，跨节点仍走 Presence/Outbox/Pending，无直接 TCP RPC）。
