## 设计决定（开卡定案，RED 前冻结）

- **D1 文件布局（prometheus/grafana 全部入库）**：
  - `docker/compose.yml`：新增 `prometheus` 与 `grafana` 两个服务声明（`network_mode: host`，与既有 gw 一致，共享宿主 loopback → 直接抓取宿主 /metrics 与对接宿主依赖）。prometheus 抓取目标指向宿主的 /metrics 端口；grafana 走 provisioning 自动加载 datasource + dashboard。镜像名用官方 `prometheus/prometheus` / `grafana/grafana`（声明入库；本环境拉取受阻，验证用 tarball 等价运行）。
  - `docker/prometheus/prometheus.yml`：`scrape_configs` 一个 job 抓取 P5-00 `/metrics`（scrape_interval 对齐 P5-00 采样节奏，`metrics_path: /metrics`），rule_files 指向 `docker/prometheus/rules/*.yml`。
  - `docker/prometheus/rules/`：告警规则文件（命名与阈值见 D2/D4）。
  - `docker/grafana/provisioning/datasources/`（datasource yaml，type=prometheus，url 指向本地 prometheus）+ `docker/grafana/provisioning/dashboards/`（dashboard provider yaml，provider path 指向 `/etc/grafana/dashboards`）+ `docker/grafana/dashboards/chat-overview.json`（dashboard JSON，经 provider 自动加载；compose 挂载 `docker/grafana/dashboards` 到 `/etc/grafana/dashboards`）。
  - `docs/observability/dashboard.md` + `docs/observability/alert-rules.md`：说明每个 panel 的 PromQL 与每条告警的触发/清除语义（供人工与 promtool 之外的断言核对）。
  - `tests/scripts/p5_01_*.py`：演练 + 断言脚本；`tests/scripts/p5_01_download_tools.sh`：tarball 下载/校验（版本 + sha256 内联）。
- **D2 告警规则文件路径与命名（冻结）**：目录 `docker/prometheus/rules/`，文件按故障域拆分——`delivery.yml`（投递停滞：outbox_lag/consumer_lag/oldest_pending_age/fencing）、`capacity.yml`（过载/拒绝：accept_rate_reject/accept_max_reject/outstanding_bytes/executor_dropped/executor_queue/pool_active）、`loop.yml`（loop 卡顿：loop_lag_ms）。告警命名 `P5_<域>_<故障>`（如 `P5_capacity_accept_rate_reject`），annotations 含 `summary`/`runbook`（runbook 指向 docs/observability/alert-rules.md 对应节）。规则格式 promtool 3.14 兼容（`groups`/`rules`，`expr`/`for`/`labels`/`annotations`）。
- **D3 prometheus.yml scrape 目标（冻结）**：本环境 /metrics 端口由 P5-00 config `metrics.port` 决定（验证时显式 `metrics.enabled=true` + 指定端口，卡内约定 `9095`）；scrape job 目标 `127.0.0.1:9095`，`metrics_path: /metrics`，`scrape_interval: 5s`（对齐 P5-00 runEvery 1s 采样并留余量），`honor_labels: true`。compose 内用宿主端口映射（host 网络直连）。
- **D4 告警阈值初值（冻结，全部标注 experimental SLO，来自 P4 故障收敛实测 E1–E4 / chaos 收敛时间）**：
  - 投递停滞类：`reliable_outbox_lag` > 收敛窗口（P4 chaos 实测收敛秒级上限，阈值取收敛上限 × 容差，如 >60s 持续 30s）、`consumer_lag` > 60（offset 差，滞后消息数非秒）持续 30s、`reliable_oldest_pending_age_ms` > 60000 持续 30s、`fencing_conflicts` 持续非零计数上升（rate>0 持续 60s）。
  - 过载/拒绝类：`accept_rate_reject` 或 `accept_max_reject` rate>0 持续 30s、`outstanding_bytes` 超过可配置字节上限持续 30s、`executor_dropped` rate>0 持续 30s、`executor_queue` 高水位持续 30s。
  - loop 卡顿类：`loop_lag_ms` > 2000 持续 10s。
  - 说明：以上初值全部标注 `experimental`；P5-02 固定 benchmark 基线产出后允许一次复核修订并记录于本卡（§9.8「实验 SLO 阈值」冻结项）。全文档**无 SLA/生产承诺措辞**——没有真实流量前只称"实验 SLO"（§9.9 停止规则）。
- **D5 dashboard JSON 结构（Grafana provisioning 冻结）**：单 dashboard JSON（`chat-overview.json`），Grafana 8+ schema（`"schemaVersion"` 兼容 provisioning 自动加载），数据源变量 `datasource` 默认指向 provisioning datasource；面板分组按故障域（Delivery / Capacity / Loop / Dependencies），每个关键信号一个 panel（对应计划 §9.3 清单：connection accept/reject rate、MessageAcceptance latency、ACK latency p50/p95/p99、oldest pending age、outbox lag、consumer lag、EventLoop lag、pool active/wait、executor queue/drop）。每个 panel 的 PromQL 在 `docs/observability/dashboard.md` 有查询断言（D6）。
- **D6 断言纪律**：dashboard 每个 panel 的 PromQL 表达式抽离为可断言查询（脚本对 prometheus 实测查询该 PromQL 断言结果类型/命名存在）；告警每条同时断言**触发证据**与**自动清除证据**（原始序列留档本卡或 reports）。
- **D7 阈值冻结边界**：任何阈值改动必须改 `docker/prometheus/rules/` + `docs/observability/alert-rules.md` + 断言脚本三处同步；本卡内初值即冻结，改动记 revision 于卡。
