## 问题与证据（实测归因）

P5-03 只修实测热点（计划 §9.5）。本卡选定台账候选二 **Outbox lease 批量 claim**，开卡读码后如实界定（luna_worker，2026-08-25）：

- **开卡前提核实：「逐条 claim」在本地 relay 不成立**——`LocalOutboxRelay::scanLocked`（LocalOutboxRelay.cpp:91-129）经 `store_.claimOutboxEvents(now, leaseOwner_, now + config_.claimLeaseMs, config_.claimBatchSize=100)` 已用**单条 `UPDATE OutboxEvent SET … WHERE processed_at IS NULL AND … ORDER BY id LIMIT ?` + 一次回读 SELECT** 完成批量 claim（MySQLMessageStore.cpp:1379-1415）。**claim 已批量**，不是本卡目标。
- **真正逐条 DB round-trip 在 processed 标记路径**：`publishAndMark`（LocalOutboxRelay.cpp:131-191）对批内每个 ok 事件循环 `store_.markOutboxProcessed(event.id, clock_.nowMs())`（:167）。每个事件一次 `finishPending()` + `pool_.acquire()` + 单条 `UPDATE … WHERE id=? AND processed_at IS NULL`（MySQLMessageStore.cpp:1417-1433）。一个 scan 批 N 个 ok 事件 = **N 次连接池获取 + N 条 UPDATE round-trip**。这是 outbox 消费路径上可批量化（单条 `WHERE id IN (…) AND processed_at IS NULL`）的 round-trip。
- **归因证据链**：
  - gprof（`/mnt/d/muduo-chat-build/p5-02-gprof-profile.txt`，reliable-direct 负载）：`MySQLMessageStore::deliveriesWhere` **4,466 次调用**；ConnectionPool 锁 churn 可见（`std::mutex::lock`/`unlock` ~93k、`std::unique_lock<std::mutex>::unlock` 32,569、`ConnectionLease::operator bool` 12,113）——DB round-trip 与连接池获取/释放是 reliable-direct durable 路径的 CPU 可见面。DB I/O wait 对 gprof 不可见（P5-02 登记），**durable 路径 DB 串行写为主成本**由 P3-11（accept 事务 3-4×SQL）/P5-02 基线承接归因。每轮 scan 的 per-event `markOutboxProcessed` 正是该主成本中可无损批量化的 DB round-trip 之一（同时削减连接池 acquire/release churn）。
  - reliable-direct 场景完整走「accept → OutboxEvent → relay claim → publish → consumer → 投递 → ACK」全路径（p5-baseline.md 场景说明），outbox 消费路径 round-trip 削减作用于该场景，且 P5-00 `/metrics` 有 `outbox_lag`/`outbox_poison` 可观测。
- **P5-03A 教训适配（本候选的失败点不存在）**：P5-03A 的 FAIL 根因 = 批量 ACK 延迟写与 DeliveryCoordinator **同步 HOL 释放语义**冲突（`acknowledge` 后 `claimFor` 需立即可见 Acknowledged 才放行下一 sequence；攒批延迟写 → 重投/重复 → 需新增写透本地 ACK 集合的状态机面，接线复杂度过高）。**markOutboxProcessed 无该耦合**：它是 relay 侧**终态幂等标记**（publish 成功后才标），没有任何「同步读 processed 状态后放行后续」的消费方——下轮 claim 只用 `processed_at IS NULL` 谓词，未标记行靠 lease 到期重领（at-least-once 语义天然兼容批量延迟）。**P5-03A 的失败点不适用于本路径**。竞争正确性由 `AND processed_at IS NULL` 守卫保持幂等（并发 relay 竞争下已标记行被跳过，与逐条语义一致）。
- **剩余候选对比（选本项理由）**：
  - **Buffer 分配复用**：gprof 归因最直接（`vector<char>::emplace_back` 317,263 / `size` 107,552 / `empty` 12,450，flat #1）；但 P5-03B 已消费「回复序列化拷贝」切片，剩余 churn 落在 mymuduo Buffer 核心（P1R-02 OutputEncoder / P1R-03 发送预算与压力回调依赖），正确性回归面大（echo/slow-consumer/backpressure/multi-reactor/TcpConnection 生命周期）、单变量性弱；且与 P5-04「Buffer 内存池化」spike（feature flag + 进入条件 = 分配次数/RSS 证明为主要瓶颈）重叠。P5-03 单变量纪律下**不选**，留作 P5-04 spike 或后续候选。
  - **锁竞争缓解**：ConnectionPool 锁 gprof 可见但属 pool 访问伴随项（本卡批量 mark 同时削减 pool acquire 次数，属部分缓解，不引入并发结构改动）；accept 事务 FOR UPDATE gprof 不可见（P3-11 归因，动 DB 事务结构风险高于本项）；registry 锁分片为并发结构改动、正确性风险最高。
  - 本项：**无 P5-03A 失败点**（终态幂等标记路径）、**DB 批量化有归因**（durable 路径 DB round-trip 主成本）、**单变量范围可控**（LocalOutboxRelay + MessageStore seam + 双 adapter + 契约测试）、**正确性面明确**（批大小 ≤ claimBatchSize 有界、lease 语义不变、竞争幂等由 SQL 守卫保证）。
- 结论：选台账候选二（Outbox lease 批量 claim），如实界定范围 = **processed 标记批量化**。若实测复测后门槛未达，循环协议第 6 步 revert + 结论入台账，另选候选——不预设结果。

## RED

**正确性 RED（批量 processed 标记契约测试）**——先写失败测试（当前只有逐条 `markOutboxProcessed`，无批量 seam 而失败），覆盖批量语义：

- **BatchMarkAppliesAll**：一批 N 事件一次批量标记全部 processed，无遗漏（等价逐条 N 次）。
- **BatchMarkIdempotent**：重复批量无副作用、时间戳不重置（已 processed 行不被覆盖）。
- **BatchMarkSkippedAlreadyProcessed**：批中含已被并发 relay 标记的行 → 该行跳过，不破坏既有 processed 行（竞争幂等，`AND processed_at IS NULL` 守卫）。
- **BatchMarkPartialSafety**：模拟 publish 部分 ok/失败（契约内直接传子集 id）→ 仅 ok 子集被标记；失败事件保持未 processed、lease 到期可重领（at-least-once 语义不破）。
- **BatchMarkEquivalentToIndividual**：批量 vs 逐条 `markOutboxProcessed` 对 outbox 状态机结果完全一致（InMemory 与 MySQL 双 adapter 契约双跑）。
- **BatchMarkBoundByClaimBatchSize**：批大小 ≤ `claimBatchSize`（100）有界。

## 最小实现（单变量）
