# Logger 同步 vs 异步性能报告

- commit: `97c0311`（P1R-08）
- 日期：2026-08-10
- 环境：WSL2 Ubuntu 24.04，kernel `6.6.87.2-microsoft-standard-WSL2`，32 vCPU，
  16 GB RAM（WSL2 环境数字不外推为裸 Linux 生产性能）
- 工具：`tools/logger-bench`（Debug 构建）
- 参数：4 线程 × 200000 条 = 800000 条；消息体 64 字节；异步队列容量 4096；
  sink = /dev/null（去除 IO 介质差异）

## 原始结果（两次运行）

| 指标 | 第 1 次 | 第 2 次 |
|---|---|---|
| sync 吞吐 | 38.9M msg/s（0.019s） | 37.9M msg/s（0.021s） |
| async 吞吐（4 线程） | 1.44M msg/s（0.556s） | 1.38M msg/s（0.578s） |
| async 调用时延 p50 | 235 ns | 250 ns |
| async 调用时延 p95 | 11.2 µs | 11.8 µs |
| async 调用时延 p99 | 56.3 µs | 58.0 µs |
| async dropped | 368192 | 360204 |

## 解读（不预设提升比例）

- **对比口径不同**：sync 模式是单线程直写（无锁、无拷贝、无队列），测的是写吞吐；
  async 是 4 线程 × 锁 × 值拷贝 × 有界队列，测的是调用方代价 + 吞吐。
- **async 的收益在调用时延与调用线程解耦**：p50 约 250ns 的调用代价（锁 + 拷贝 +
  入队）不随 sink 介质变慢而增长——同步直写则被 IO 阻塞线性拖慢（本 bench 用
  /dev/null 掩盖了该差异）。
- **dropped ≈ 36-46%**：容量 4096 的突发生产（80 万条瞬间涌入）下按 drop policy
  丢弃，计数可查（droppedCount）——有界性按设计工作，非缺陷。
- **完成定义核查**：无"未解释"的性能回退——异步吞吐低于单线程直写可完全解释为
  锁/拷贝/队列成本与并发生产者开销；调用时延（250ns 级）远低于同步 IO 阻塞路径。
- 生产参数（容量、线程数、批大小 64）需按真实负载另行测量，本报告不给出建议值。
